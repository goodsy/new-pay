# PayCore 최초 구현 범위 권장안

2026-10-03 KST / 상태: 제안, 사용자 확정 전

1~5번 기본 방향과 결제 허용/기관 연동 규칙은 앞선 사용자 결정으로 확정됐다. 아래 통화·카드 범위·할부·인증 흐름은 추가 채택 대상이다. 실제 기관 규약과 운영 수치를 임의 확정하지 않는다.

## 1. 최초 출시 목표

| 항목 | 권장 범위 |
|---|---|
| 거래 통화 | KRW, 원 단위 정수, 양수 |
| 정산/지급 통화 | KRW |
| 카드 | 국내 발급 신용카드 + 체크카드. 지원 카드사/상품은 기관 프로파일의 allowlist |
| 일시불 | 신용카드·체크카드 지원 |
| 할부 | 기관/카드/가맹점이 허용하는 일반 유이자 할부. 체크카드 할부 금지 |
| 취소 | 원 거래의 전액/부분취소, 기관 지원 범위 내 |
| 인증 | PG 결제창 → 카드사/인증기관 인증 → 가맹점 서버 확인 → PG 승인 |
| 채널 | 웹·모바일 웹. 앱카드 인증은 기관 연동 경계로 표현 |
| 초기 제외 | 해외 발급/외화/환전, 무이자·부분무이자 프로모션, 빌링·수기/비인증 결제, 카드포인트 복합결제, 기프트/선불/직불망 카드, 부분 승인·다중 수단 분할 결제 |

법인카드는 별도 출시 보장을 하지 않고 기관 프로파일에서 지원되는 인증/일시불 상품만 허용한다. 복잡한 법인 인증·상품별 할부는 후속 확장한다. 국내 발급 카드의 해외 브랜드 로고만으로 해외 카드로 분류하지 않는다. 상품/발급국/처리망을 기관 근거로 판정한다.

## 2. 구현 순서와 할부 계약

최초 수직 기능은 KRW 신용카드 일시불로 만든다. 전체 자금 흐름·UNKNOWN·취소 검증 후 체크카드 일시불과 일반 할부를 추가한다. 이는 개발 순서이며 권장 출시 목표를 일시불만으로 제한한다는 뜻은 아니다.

할부는 일시불과 구별하는 PaymentPlan으로 표현하고 실제 전문의 00/0 등 표현은 Adapter에서 변환한다. 할부 가능 개월, 최소금액, 카드/상품 제한, MID 계약 지원을 버전 있는 Capability/정책으로 관리한다. 운영 개월 수와 최소금액은 실제 기관 규약을 확인해 결정한다. 체크카드 또는 미지원 개월 요청은 PG 단계에서 거절하며 기관에도 재검증을 요구한다.

할부 개월/상품을 인증 세션·승인 요청·기관 결과·Route 근거에 연결한다. 고객 요청을 기관이 다른 조건으로 처리하면 조용히 덮어쓰지 않고 상충 결과로 조사한다. 승인 이후 조건 변경은 새 구매 흐름이며, 원 승인 근거를 수정하지 않는다. 일반 할부와 가맹점 부담 무이자/부분무이자의 비용·정산 처리는 별도 모델로 확장한다.

## 3. 고객 인증과 승인 흐름

1. 가맹점 서버가 주문·금액·통화·MID·Site·상품명 등을 검증하여 결제 세션/Payment를 만든다. 실제 금액은 서버에서 보존한다.
2. PG 결제창은 제한된 세션 토큰으로 카드사·가능한 PaymentPlan을 선택하게 한다. 토큰은 주문·Payment·MID·금액·통화·환경·만료에 바인딩한다.
3. PG가 기관 프로파일에 맞는 인증 시작 Adapter를 호출하고 인증기관 화면/앱으로 연결한다. 카드 소유자 인증을 자체 로그인/일반 SMS OTP로 대체하지 않는다.
4. 인증 결과를 서버에서 서명/기관 조회/약정된 증거 방식으로 확인한다. 브라우저 successUrl의 성공 표시만 신뢰하지 않는다. state/nonce, 요청 ID, 원 세션, 금액·통화·MID·선택 조건, 유효기간을 대조한다.
5. 인증 완료 상태를 별도 AuthenticationSession에 영속화한다. 인증 성공은 Payment 승인 성공이 아니다. Payment는 이 단계에서 REQUESTED를 유지할 수 있다.
6. 가맹점 서버가 주문의 현재 유효성과 보존 금액을 확인하고 동일 멱등키로 PG 승인 API를 호출한다. 이 호출의 timeout은 새 결제를 만드는 근거가 아니다.
7. PG는 주문 슬롯·4번 허용 조건을 다시 판정하고 인증 근거를 승인 operation에 원자적으로 귀속한다. 승인 실행 Attempt를 저장한 뒤 소켓으로 가상 VAN에 보낸다.
8. 결과를 PAYMENT 로컬 TX로 확정하고 가맹점 서버 조회/서명된 Webhook으로 전달한다. 가맹점은 승인 확정 후 주문 완료/상품 제공을 진행한다. UNKNOWN은 확인 중으로 표시한다.

AuthenticationSession은 CREATED/IN_PROGRESS/VERIFIED/FAILED/EXPIRED 같은 별도 인증 lifecycle를 갖는다. 인증 근거의 만료·실패와 외부 승인 결과는 구분한다. 인증 성공 후 TTL 만료만으로 이미 전송한 승인을 FAILED/EXPIRED로 바꾸지 않는다.

같은 인증 근거는 하나의 논리 승인 operation에만 연결한다. 동일 operation 복구/재요청은 기존 결과를 사용하며 신규 승인 권한을 만들지 않는다. 전송 전 재시도에도 기관의 인증 근거 재사용 규약이 적용된다. 만료시간·자동 승인 호출 여부는 계약에서 확정하되 기본 권장안은 가맹점 서버 confirm 방식이다.

## 4. 가상 인증기관

가상 VAN과 구별되는 인증 Adapter/Simulator 역할을 둔다. 초기에는 같은 Simulator 배포에 있어도 인증 사실과 승인 원장은 분리한다.

- 가상 카드 참조로 국내 신용/체크, 지원/미지원 상품, 인증 성공/실패/사용자 취소/만료를 재현한다.
- issuer/acquirer/authenticationProvider를 구분해 이름이 다를 수 있는 경로도 시험한다.
- 서명된 일회성 인증 근거 또는 서버 조회 가능한 opaque token을 제공한다. 실제 카드번호·CVC·인증 비밀번호는 필요 없다.
- 중복 callback, 잘못된 금액/MID, state 불일치, 늦은 결과, 인증 후 가맹점 confirm 유실, 인증 근거 재사용을 시험한다.
- 카드사 앱/인증 서비스를 실제로 복제했다고 주장하지 않는다. 실제 전환 시 해당 기관 인증 모듈·보안·규약을 연동하고 인증시험을 수행한다.

## 5. 확장 경계

- Money는 amount+currency이며 초기 검증은 KRW 소수 금지다. 미래 외화의 소수 단위·거래/정산통화·환율은 별도 확장한다.
- CARD 아래 cardType(CREDIT/CHECK 등)과 issuer/acquirer를 구별한다. 카드 종류의 최종 근거는 기관 결과이며 클라이언트 선택만 신뢰하지 않는다.
- PaymentPlan, CardAuthenticationPort, AuthorizationPort, AcquisitionPort를 분리한다. 국내 카드 인증을 모든 결제수단의 필수 공통 절차로 만들지 않는다.
- 실제 인증 암호화/전문 규약은 Adapter 경계이며 Domain에 인증 SDK 타입을 노출하지 않는다.

## 6. 완료 검증

신용/체크 일시불, 일반 할부 허용·거절, 체크 할부 거절, 금액/통화/조건 바인딩 위반, 만료·callback 중복·재사용, 인증 성공≠승인 성공, 가맹점 confirm timeout·UNKNOWN 복구, 승인→취소→매입→입금→정산→지급→대사를 검증한다.
