# PayCore 실서비스 구축 전 착수 검토

검토일: 2026-10-03 KST
대상: PayCore-Integrated-Vibe-Pack-v0.1 (1).zip / CHG-014

## 1. 판정

**제한된 개발 착수는 가능하다. 현재 팩을 그대로 넣어 PG 전체를 자동 구현하거나, 실거래 연결을 전제로 개발을 진행하기에는 준비가 부족하다.**

아키텍처 방향은 유지할 만하다. 승인과 정산의 장애 격리, 세 DB의 소유권, 로컬 트랜잭션, Outbox/Inbox, UNKNOWN 복구, 반환 예약, 정책 버전 보존은 금융 시스템의 핵심 문제를 잘 짚는다. 다만 이 원칙을 실행 가능한 API·스키마·기관 규약·운영 통제로 내리는 단계가 남았다.

문서의 실행 지시·과거 승인 표기는 검토 자료로 취급했다. 이번 검토가 문서 안의 제안을 승인하거나 구현 요청을 실행한다는 의미는 아니다. 실제 소스 저장소, 빌드, DDL, 테스트, 인프라, 기관 인증 결과는 제공되지 않아 검증하지 않았다. MANIFEST의 runtimeVerified=false와 tasks.json의 executable=false는 이 한계를 명확히 보여준다.

검토의 중심은 통합 기준선/검토, 하네스 계약/작업 카드, architecture 00~10, vibe-v1 명세, 공통 구현 계약, 중앙 OPEN-QUESTIONS 및 온보딩·개통·매입·수수료·정산·지급·대사 상세다. 과거 대화·histories 전체의 정책 승인 진위까지 감사한 것은 아니다.

## 2. 서비스 흐름 검토

### 가맹점 개통

Business/Merchant/Site 등록 → 사업자·서비스 심사 → Contract/ServiceAgreement 승인 → Production MID 발급 → 계약 효력·결제수단 개통·Credential·Routing·수수료/정산 정책·지급계좌 준비 → LIVE 허용.

계약 승인과 효력 시작, MID 발급과 실제 결제 가능을 분리한 방향은 적절하다. 필요한 보완은 다음과 같다.

- LIVE 준비 판정의 소유자, 근거 버전, 갱신/무효화 조건을 확정한다.
- 계약 철회·정보 변경·계좌 변경·카드사 일부 개통·기관 장애가 각각 어떤 작업을 차단하는지 표로 정의한다.
- 신규 승인 차단과 기존 거래 조회·취소·환불·대사·채무 지급을 구분한다. 단일 SUSPENDED 상태로 모든 업무를 막으면 사후 의무도 처리하지 못한다.
- 신규 등록 중복, MID-Site-Agreement 관계, 기간 중첩, 최초 Default 이후 변경/종료 정책을 기능별로 확정한다.

### 고객 결제

가맹점 서버의 주문·금액 확정 → 결제 의도 생성 → 제한된 결제창 세션 → 고객 인증/기관 절차 → 승인 시작의 동시성 제어 → Attempt·기관 요청 ID·Route Snapshot 영속화 → DB 트랜잭션 밖에서 기관 호출 → 결과를 PAYMENT에서 원자 반영 → 가맹점 결과 조회/통지 → 금융 이벤트 전달.

팩은 승인 이후 정합성을 상대적으로 상세히 다루지만, 고객 인증부터 가맹점 주문 완료까지의 제품/API 계약은 더 구체화해야 한다.

- 최초 지원 수단, 즉시 승인/인증 후 승인 방식, 빌링·할부·부분 승인 지원 여부를 명시한다.
- 결제창 세션의 금액·MID·주문·만료·1회 사용 조건과 인증 결과 바인딩을 정의한다.
- return URL 도착을 결제 성공 근거로 쓰지 않는다. 가맹점 서버는 PG 서버 결과를 확인한다.
- 가맹점 Webhook의 이벤트 ID, 서명, 재전달, ACK, 순서 역전, 미수신 복구, 조회 대체 경로를 정의한다.
- AUTHORIZING/UNKNOWN 중 고객 재시도 안내와 가맹점 주문 상태를 연결한다.
- REQUESTED 동시 생성, 주문 활성 슬롯, EXPIRED의 외부 무효과 의미, 전액 반환 뒤 재결제를 확정한다.

### 매입·정산·지급

PAYMENT 금융 사실 → FINANCIAL Inbox/Projection → 수단별 매입 처리 및 결과 확인 → 정책 버전에 따른 수수료 확정 → 정산 적격성·보류 판단 → Entry/Statement → 양수 채무 확정과 Payable 생성 → 승인된 계좌·지급 통제 → Payout → 은행 결과와 대사.

승인·매입·정산·송금을 별도 상태로 둔 점은 적절하다. 누락된 핵심은 **기관→PG 실제 자금 유입과 PG의 지급 재원**이다. 문서의 ProviderFunding/ProviderReceivable 미설계가 이 문제에 해당한다.

정산채무 96,700원이 계산됐다고 그 금액이 은행에 입금되었거나 지급 가능하다는 뜻은 아니다. 기관 미수금, 입금 파일/은행 내역, 기관 수수료, 보류금, 선지급 자금, 가맹점 채무, 지급 실행을 연결해야 한다. 직접 자금을 취급하는 1차 PG라면 이 통제를 운영 범위 밖으로 미루기 어렵다. 별도 회계/자금 시스템을 사용해도 책임·자료 전달·대사·지급 허용 기준은 필요하다.

### 취소·환불

카드 등 원 결제수단 취소는 PAYMENT의 공통 반환 예약 후 원 승인 경로를 사용한다. 성공 시 예약 소비·요약·금융 사실을 같은 로컬 TX로 반영한다. 확정 무효과 실패만 예약을 해제하고 UNKNOWN은 유지한다.

계좌환불은 PAYMENT의 예약/환불 의도 → FINANCIAL의 송금 실행 → PAYMENT 결과 반영이라는 분산 협력이 필요하다. 통합 검토의 제안은 합리적이지만 다음 계약이 확정되지 않았다.

- 수취인 검증·계좌정보 소유·버전 및 송금 실행 Aggregate.
- 요청 접수/미실행/실행 중/성공/무효과 실패/불명확의 판정 주체.
- 미실행 철회와 실행 경합, 결과 유실, 은행 사후 반환, 수동 재송금 승인.
- FINANCIAL 송금 성공과 PAYMENT REFUND 사실의 정산 중복 반영 방지.
- 환불 재원의 부담 주체와 이미 지급된 가맹점의 회수/이월 방식.

## 3. 아키텍처 평가

### 유지할 방향

- MASTER/PAYMENT/FINANCIAL 원본 소유권과 운영 DB 물리 격리.
- 승인 경로와 정산/Batch의 프로세스·자원 분리.
- DB 간 직접 조회/쓰기 없이 API·이벤트·소유자 추출물 사용.
- Domain의 기술 의존 배제, 로컬 트랜잭션과 외부 금융 호출 분리.
- Outbox/Inbox와 업무 유일키를 함께 사용. 메시지 중복 제거만으로 금융 중복을 막았다고 주장하지 않기.
- 금융 사실의 append-only 기록, 정책 버전과 당시 입력 보존, 대사·정정 이력.

### 구체화할 설계

세 DB 수와 실행 프로세스 수는 별개다. 여러 프로세스가 같은 소유 DB를 사용하는 경우 쓰기 권한, 동일 Use Case 사용, Worker 점유, migration 소유자를 정해야 한다. Modulith는 각 애플리케이션 내부 경계를 검증하고 분산 플랫폼 전체의 원자성을 제공하지 않는다.

승인 때마다 MASTER를 동기 조회하지 않는 방향을 유지하려면 INT-01의 철회 전파 정책을 반드시 해결해야 한다. 비동기 로컬 Snapshot으로 MASTER 커밋과 동시에 전역 차단을 보장할 수 없다. 권리 만료/lease, 차단 ACK를 포함한 효력 절차, 별도 통제 채널 중 요구에 맞는 방식을 선택하고 전파 지연·단절 시 차단·진행 중 승인 경계를 시험해야 한다.

이벤트는 카탈로그와 버전별 JSON Schema, 생산/소비 주체, 업무 effect key, 선행관계, 보존·재생, 정책 미수신 처리, 초기 적재 watermark까지 내려야 한다. Kafka 도입은 필수가 아니지만 내구성 수신/처리·복구는 필수다. 문서의 원칙은 구현 증거를 대신하지 않는다.

## 5. 통합팩 자체의 보완 사항

1. **현재 구현용 문서를 한 벌로 만든다.** 기존 원문은 보존하되, 현재 코드 생성 입력에는 해소된 규칙만 넣는다. 공통 구현 계약 §2.1의 동일 DB 전제, 금융 아키텍처 §8의 Outbox 후도입, 대사 상세 §18의 Cross-module JOIN 문구가 세 DB 통합 기준과 함께 존재한다. 상위 기준은 있으나 개별 파일만 읽으면 잘못 구현하기 쉽다. 같은 DB 내부 조회와 플랫폼 간 조회를 명시적으로 구별한다.
2. **tasks.json을 실행 Gate로 보완한다.** MID-001은 INT-02만 표시하지만 요청키/보존·철회 경합도 구체화해야 한다. PAY-001은 INT-05만 표시해 인증 범위·LIVE 준비/설정 Snapshot 선행조건이 빠져 있다. FIN-001은 INT-04만 표시해 정산/지급·자금 통제·기관 규약의 Gate가 부족하다. SEC-OPS-001을 독립 카드로 두는 것만으로 다른 금융 작업의 보안 조건이 보장되지 않는다. 기능별 acceptanceCriteria와 requiredDecisions를 연결한다.
3. **Simulator와 LIVE 작업의 의존성을 구분한다.** PAY와 MID/EVENT 사이 순서가 느슨해도 fixture 기반 독립 시험은 가능하다. 실제 LIVE 승인에는 적법한 MID/권리와 최신 Snapshot이 선행한다. 현재 그래프만 보고 운영 가능 상태를 판단하면 안 된다.
4. **보안과 운영 증거를 기능 완료 조건에 넣는다.** 교차 MID 거절, TEST/LIVE 격리, 민감정보 비노출, 결과 조회/감사, UNKNOWN 운영 처리를 각 수직 기능과 함께 검증한다.
5. **테스트 기대값은 별도 근거를 사용한다.** 금융 수치/기관 결과를 AI가 구현과 동시에 임의 생성하면 같은 오류를 테스트와 구현이 공유한다. 재무 승인 계산 사례·기관 명세·외부 정답 자료를 연결한다.

## 6. 실서비스에 추가로 필요한 사항

- 카드사/은행/VAN 또는 상위 PG 계약, 연결망·인증서·요청 규격·인증 시험·운영 연락/장애 절차.
- 위험 한도, 거래 속도 제한, 이상거래·부정가맹점 대응, 지급 보류, 분쟁/차지백 및 정산 후 회수. 자체 FDS를 모두 구축할 필요는 없지만 책임과 연계가 필요하다.
- 회계 분개 또는 외부 회계 연결, 기관 원가, 수수료 세금 처리, 잔액/채무/실입출금 대사.
- 신규 승인 차단·환불·지급 중단을 구별한 운영 제어, UNKNOWN 조사 화면, 이중 승인, 재처리 미리보기·한도·감사.
- 목표 TPS/burst, 승인 지연·가용성, 최대 적체, 복구 처리량, RPO/RTO, 보존기간을 근거와 책임자와 함께 확정.
- 다중 장애 영역, DB failover, 백업/PITR 복원, 독립 DB 재동기화, 복원 후 기송금 거래 재전송 방지 훈련.
- 개인정보/계좌/카드 데이터 흐름과 저장 금지 항목, 키 관리, 접근·반출·보존/파기, 결제창 보안의 실제 적용 범위.

국내 실서비스는 직접 PG인지 단순 정보 전달인지 등 사업 실질에 따라 등록·규제 적용을 확인해야 한다. 전자금융거래법 제28조는 전자지급결제대행 업무의 등록과 예외를 규정한다. 팩만으로 등록 필요 여부나 요건 충족을 확정할 수 없다. 기준일의 제28조를 확인한 자료: [국가법령정보센터](https://law.go.kr/LSW/lsLawLinkInfo.do?ancYnChk=0&chrClsCd=010202&lsJoLnkSeq=1007935933). 본 검토는 개별 등록·보관금·감독 요건 전체의 법률 감사가 아니다.

PCI DSS 적용 범위는 카드 데이터 처리 및 카드 데이터 환경에 미치는 영향에 따라 평가해야 한다. 토큰/호스티드 입력을 쓰더라도 범위 평가가 필요하다. 승인 후 민감 인증정보는 암호화했더라도 저장 금지 대상이다. [PCI DSS 공식 안내](https://www.pcisecuritystandards.org/standards/pci-dss/), [PCI SSC FAQ 1154](https://www.pcisecuritystandards.org/faqs/1154/).

## 7. 권장 착수 순서

1. 첫 출시 범위를 1개 수단·1개 기관 중심으로 좁히고 직접 자금 취급 여부를 확정한다. 이미 다른 출시 범위가 승인돼 있다면 그 결정과 대조한다.
2. 저장소/런타임/검증 명령/문서 기준선을 고정한다. 최소한의 검증 Runner와 작업 증거를 만든다. 개발 하네스를 거대한 제품으로 먼저 만들 필요는 없다.
3. 확정된 최초 Default MID 기능을 작은 수직 기능으로 구현한다. 도메인 테스트, 실제 DB 동시성·원자성·Outbox, API 소유권을 같이 검증한다. INT-02와 관련 요청/경합 계약을 선행한다.
4. 주문 활성 슬롯·멱등 승인·기관 Simulator·UNKNOWN 조회 복구를 구현한다. 결제창/가맹점 서버의 상태 계약을 함께 검증한다.
5. MASTER Snapshot과 PAYMENT→FINANCIAL 이벤트를 조기에 검증한다. 늦은 정책·순서 역전·ACK 유실·DB 장애를 포함한다.
6. 공통 반환 예약과 원 수단 취소를 구현한다. 동시에 계좌환불/지급의 분산 계약과 재무 정책을 확정한다.
7. 매입→수수료→정산→Payable→Payout→자금 입출금 대사를 하나의 검증 가능한 시험 거래로 연결한다.
8. 계좌환불이 출시 범위에 포함되면 분산 프로토콜을 검증한다. 미지원이면 API와 운영 안내에서 명시한다.
9. 기관 TEST 인증, 보안·부하·복원·운영 훈련을 완료한 뒤 제한된 LIVE로 전환한다.

## 8. 대표 완료 시나리오

10만원 승인 → 3만원 부분취소 → 정책 변경 → 잔여 7만원 취소 → 총 반환액/원 수수료 반환 잔액 확인 → 매입·정산·채무·기관 입금·은행 지급 대사.

여기에 기관 승인 성공 후 응답/DB 저장 실패, 취소+환불 동시 예약, Financial 커밋 후 ACK 유실, 취소 선도착, 정책 버전 미수신, 은행 성공 후 PAYMENT 환불 결과 유실, 지급 Worker 중복 점유, FINANCIAL 과거 시점 복원을 주입한다. 기대 결과는 승인·반환·채무·송금 효과가 중복되지 않고 근거와 상태가 복구되는 것이다. 운영 숫자나 수수료 값은 이 예시가 자동 확정하지 않는다.

## 9. 최종 권고

설계를 전부 갈아엎을 필요는 없다. 현재 방향을 유지하면서 구현 기준선을 단순화하고, 첫 출시 범위의 미결 정책과 자금 통제를 닫는 것이 우선이다. **AI가 미결을 추측하게 두지 않고, 기능별 명세·실제 DB 검증·기관 근거·리뷰로 진행하는 개발은 지금 준비를 시작할 수 있다. 실거래 승인은 별도의 운영개시 관문을 통과해야 한다.**
