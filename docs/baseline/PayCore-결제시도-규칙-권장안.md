# PayCore 결제 시도 규칙 — 확정

2026-10-03 KST / 상태: 사용자 확정 / 범위: 국내 카드 최초 구현

사용자가 이번 대화에서 “이안으로 해줘”로 본 권장안을 채택했다. 아래 업무 규칙을 구현 기준으로 사용한다. 파일명은 기존 링크 유지를 위해 보존한다. 기관별 실규약과 DB 구현 방식은 별도 검증 대상이다.

## 1. 기본 모델

- OrderKey = (environment, merchantAccountId, merchantOrderId). 주문은 MID 범위다. 다른 MID로 요청을 옮기면 별개의 키가 되므로 같은 구매의 MID 변경은 가맹점 주문 시스템이 별도로 통제한다.
- 주문 하나에 Payment 이력은 1:N으로 둔다. Payment는 고객의 한 결제 시도이며 새 시도에는 새 paymentId/paymentKey를 부여한다.
- 주문당 활성 Payment는 하나로 제한한다. REQUESTED도 활성에 포함하여 중복 결제창을 제어한다. 기존 활성 결제의 같은 내용 재요청은 기존 Payment/operation을 반환하고 다른 내용이면 충돌로 거절한다.
- 최초 구현은 Payment당 논리 Authorization 하나다. 여러 AuthorizationAttempt는 허용하지만 동시에 실행 중인 외부 승인 Attempt는 하나다. 고객이 카드를 바꿔 새로 결제하는 경우 무효과 종결 확인 후 새 Payment를 만든다.
- 최초 구현은 요청 전액 승인만 허용한다. 부분 승인·다중 수단 분할 결제는 미지원으로 명시한다. 기관이 예기치 않은 금액을 승인했다고 보고하면 무시하거나 일반 성공으로 처리하지 않고 원본 근거를 보존하여 예외 복구/대사를 수행한다.

## 2. 상태별 새 시도

| 기존 Payment | 같은 주문의 새 Payment | 처리 |
|---|---|---|
| REQUESTED | 금지 | 같은 내용이면 기존 시도 재사용. 안전하게 종료/만료된 후 새 시도 |
| AUTHORIZING | 금지 | 원 operation 상태 조회 |
| UNKNOWN | 금지 | 원 Attempt 조회·통보·대사로 결과 확인 |
| AUTHORIZED | 금지 | 기존 성공 반환. 취소/환불 여부와 무관하게 성공 주문 이력 유지 |
| FAILED | 조건부 허용 | 기관의 확정 거절 또는 외부 효과 없는 종결이 확인된 경우 |
| EXPIRED | 조건부 허용 | 미전송이며 재사용 가능한 인증/세션이 폐기됐거나 기관 무효과 종결이 확인된 경우 |

Payment FAILED는 자동으로 기관 장애/timeout을 뜻하지 않는다. Authorization DECLINED와 기술 실패는 진단·이력에서 구분하지만 새 고객 시도는 기존 금융 효과가 없다는 근거가 있어야 한다. 단순 NOT_FOUND는 기관의 조회 지연·최종성 규약 확인 전 무효과 근거가 아니다.

## 3. 만료·재결제

- 결제창/인증 세션의 만료와 금융 결과 확정을 구분한다. 이미 전송했거나 전송 여부가 불명확한 Attempt는 시간 경과만으로 EXPIRED/FAILED로 전환하지 않는다.
- REQUESTED 종료/만료와 승인 시작은 동일 주문 슬롯/Payment 상태에 대해 직렬화한다. 오래된 결제창의 승인 요청은 다시 승인할 수 없다.
- 만료시간의 실제 수치는 기관 인증 규약과 제품 요구를 확인해 별도 정책으로 정한다. 이 제안은 운영 TTL을 임의 지정하지 않는다.
- 전액 취소·환불 후 다시 구매한다면 새 merchantOrderId를 사용한다. 기존 주문의 반환 상태 FULL을 새 승인 허용 조건으로 사용하지 않는다.
- 승인된 주문의 금액·통화·MID·Site 등 결제 근거는 변경하지 않는다. 같은 주문의 재시도도 원 주문의 금액·통화·Scope를 유지한다. 변경 주문은 새 주문 ID를 사용한다.

## 4. 기관 재시도와 UNKNOWN

- 복구 조회와 신규 금융 요청을 분리한다. UNKNOWN에서 새 승인·다른 VAN failover·고객 새 시도를 보내지 않는다.
- 기관 재시도는 전송 전 실패가 확정됐거나, 원 승인의 무효과 종결 및 재요청 안전성이 기관 규약상 확인된 때만 허용한다.
- 새 Attempt를 만드는 것이 반드시 새 providerRequestId를 만드는 뜻은 아니다. 기관의 동일 ID 재전송/새 ID 규약에 맞춘다. 내부 업무 ID와 기관 요청 namespace를 각각 보존한다.
- 응답·통보·조회가 상충하면 기존 금융 사실을 덮어쓰지 않고 증거와 예외 상태를 남긴다. 확정 거절/만료 뒤 늦은 성공은 계약 가정 위반 사건으로 처리하며 주문의 추가 승인 차단·조사·대사를 수행한다. 자동 보상취소 여부는 별도 정책이다.
- 기관 거절은 일반적인 VAN 우회 근거가 아니다. 카드 재입력은 새 고객 시도로 처리한다.

## 5. 동시성과 멱등성

- Payment별 낙관적 잠금만으로 다른 Payment 사이 중복 승인을 막을 수 없다. OrderKey별 영속 슬롯을 두고 활성 시도 점유·해제·승인 시작을 잠금/조건부 쓰기로 직렬화한다.
- API 멱등키는 (environment, authenticated MID, operation, idempotencyKey) 범위이며 정규화된 payload fingerprint를 비교한다. 같은 키/다른 내용은 충돌이다. 동일 키 재조회에도 현재 조회 권한을 검사한다.
- 다른 멱등키로 들어온 같은 주문 생성 요청도 활성 슬롯으로 제어한다. payload가 동일하면 기존 활성 시도로 연결하고 다르면 충돌을 반환한다.
- 요청 기록/캐시 만료와 영구 금융 사실/업무 유일성을 구분한다. 보존기간은 별도 정책이며 캐시 삭제로 승인 이력을 잊지 않는다.
- 승인 Attempt·Route Snapshot·operation 점유를 PAYMENT TX1에서 커밋하고 기관은 TX 밖에서 호출한다. 결과 확정 TX2에 Authorization/Attempt 결과·Payment 요약·PaymentTransaction·요청 결과·Outbox를 함께 반영한다.
- 동일 최종 결과의 응답/통보/조회 중복은 한 금융 효과만 만든다. 이미 반환된 과거 성공 응답과 현재 상태 조회를 구분한다.
- 재생/조회 복구가 기관 승인을 새로 실행하지 않는다.

## 6. 필수 테스트

1. 다른 멱등키로 같은 주문 생성 2건: 같은 활성 Payment로 수렴하거나 충돌하며 활성 슬롯 하나.
2. 승인 시작 동시 요청: 기관 승인 실행 하나.
3. 승인 시작과 만료/종료 경합: 한쪽만 유효한 상태 전이, 만료 후 오래된 화면의 승인 금지.
4. 기관 승인 성공 후 timeout/DB 저장 실패: 새 승인 없이 원 Attempt 결과 복구, 금융 사실/Outbox 한 번 반영.
5. UNKNOWN 중 새 카드·새 키·다른 VAN 요청: 신규 승인 차단.
6. 확정 거절 후 새 Payment: 성공 가능, 과거 이력 보존.
7. 승인 성공 이후 전액 취소: 기존 주문 새 승인 차단, 새 주문으로 구매 가능.
8. 같은 키 또는 같은 주문의 다른 금액·통화·Site: 충돌.
9. 늦은 성공/역순 결과/기관 NOT_FOUND: 무조건 실패·무조건 상태 덮어쓰기 금지, 근거 기반 복구.
10. 다른 MID/TEST-LIVE 간 조회·승인: 인증/환경 범위 거절.

## 7. 구현 전 남은 입력

본 안의 채택으로 INT-05의 주요 업무 선택(주문당 활성 시도 하나, REQUESTED 포함, 만료의 무효과 조건, 전액 반환 후 새 주문 사용)을 확정했다. 기관별 무효과 판정/안전 재시도(INT-06), 계약·키 차단 전파(INT-01), LIVE 준비 조건, 실제 금액·통화/인증 세션 API 및 상태 전이의 DB 설계는 별도 확정·검증해야 한다. 모든 Gate가 자동 해결됐다는 뜻은 아니다.
