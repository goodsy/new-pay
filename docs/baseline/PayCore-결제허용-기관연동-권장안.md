# PayCore 실제 결제 허용 조건·기관 연동 계약 — 확정

2026-10-03 KST / 4·5번 상세 규칙: 사용자 확정 / 가상 기관 연동 및 통신 교체 방향: 사용자 지정

사용자가 이번 대화에서 “4,5권장안 으로 확정해줘”로 본 안을 채택했다. 아래 실제 결제 허용·차단, 기관 연동 경계 및 가상 기관 검증 규칙을 구현 기준으로 사용한다. 파일명은 기존 링크 유지를 위해 보존한다. 본문에서 별도 정책/검증 대상으로 명시한 운영 수치·진행 중 승인 성공의 사후 처리·실제 기관 규약은 자동 확정하지 않는다. 실제 기관 인증이나 운영 준비 완료를 의미하지 않는다.

## 4. 실제 결제 허용 조건

### 4.1 신규 승인 조건

다음 조건을 모두 충족한 경우에만 신규 승인 전송을 허용한다.

1. 신뢰된 인증 주체의 MID·환경·operation 범위가 일치하고 Credential이 유효하다.
2. Business/Merchant가 신규 결제를 허용하는 상태이며 법적 주체·서비스 제한에 걸리지 않는다.
3. MID가 발급 완료 상태이고 운영 중지/종료가 아니다. 발급 완료만으로 결제를 허용하지 않는다.
4. Contract/ServiceAgreement가 승인됐고 효력 기간 내이며 필요한 카드 서비스 권리가 유효하다.
5. Site가 MID와 같은 Merchant 소속이고 계약 Scope·유효 연결 범위를 충족한다. Site 대상 계약은 해당 Site 거래만 허용한다.
6. 실제 사용할 카드사/서비스/Route의 개통·심사 근거가 유효하다. 카드 일부 개통은 개통된 카드사/Route만 사용한다.
7. 주문·금액·통화·결제 입력/인증 세션의 바인딩과 만료를 검증했다. 고객 인증 방식은 최초 기관 규약에 맞춘다.
8. 해당 거래의 Route/기관 계정·Credential이 준비됐고 전송 전 Health 정책을 충족한다.
9. 승인에 적용할 수수료·정산 정책의 명시적 버전/Assignment를 확보했다. 승인 단계에서 최종 수수료를 계산할 필요는 없으나 계산 근거 버전은 남긴다.
10. 가맹점 개통 시 지급계좌 및 정산 준비가 검증됐다. 계좌 변경/오류가 이후 신규 승인까지 차단하는지 또는 지급만 보류하는지는 별도 운영 정책으로 판정한다.
11. 주문 활성 슬롯 및 기관 승인 실행 점유에 성공했고 중복 승인/UNKNOWN이 없다.
12. 로컬 권리 Snapshot/승인 허용 lease가 유효하고 긴급 차단 목록에 없다. 필수 설정 누락/지원하지 않는 버전은 차단한다.
13. 거래 한도·위험 통제, PAYMENT 저장/Attempt 영속화 등 안전하게 처리할 인프라 조건을 충족한다.

이 판정의 소유자는 PAYMENT 승인 Use Case다. MASTER는 계약·개통·정책의 원본과 버전 있는 권리 근거를 발행한다. API Gateway나 결제창의 앞단 검사는 최종 판정을 대신하지 않는다. 판정 입력·권리/정책/Route 버전과 판정 시각을 Attempt에 연결한다.

### 4.2 Snapshot과 차단 전파

- 평상시 승인 요청마다 MASTER를 필수 동기 조회하지 않는다. 검증된 로컬 Snapshot과 만료 있는 권리 lease를 사용한다.
- 권리 차단 버전은 뒤늦게 도착한 과거 허용 이벤트로 되돌릴 수 없다. 재승인은 새 버전과 재검증을 요구한다.
- 만료된 권리·필수 Snapshot 누락·확인할 수 없는 버전은 신규 승인 차단이다. MASTER 단절은 유효 lease 기간 동안만 제한적으로 허용한다.
- lease 갱신은 MASTER의 최신 권리와 연결한다. 철회 이후 기존 권리를 다시 갱신하지 않는다.
- 긴급 MID/키 차단은 우선 전파하고 PAYMENT 각 처리 인스턴스의 적용 ACK를 관측한다. 신규/재시작 인스턴스는 현재 차단 상태를 적재하기 전 트래픽을 받지 않는다.
- 철회 요청 접수, MASTER 권리 차단 커밋, 전체 차단 효력 확인은 구분한다. 전체 효력 확인은 관련 실행 인스턴스의 ACK 또는 기존 허용 lease 만료/격리가 확인된 뒤 기록한다. 단순 이벤트 발행을 전역 차단 완료로 표시하지 않는다.
- 전역 차단 효력 완료 뒤 새 승인 전송이 없도록 진행 중 미전송 작업도 포함해 전송 게이트/실행 점유를 통제한다. 각 인스턴스의 drain/ACK 또는 fencing 절차를 검증한다.
- 이미 기관에 전송됐거나 전송 여부가 불명확한 승인은 원 결과를 복구한다. 철회/TTL을 근거로 실패 처리하거나 자동 취소하지 않는다. 계약 철회 중 승인 성공의 사후 처리는 별도 업무 정책이다.
- 외부 통신과 로컬 차단 커밋을 하나의 TX로 보장할 수 없다. 수신 즉시 로컬 차단과 확정된 전역 차단 효력의 차이를 운영 화면에서 표현한다.

허용 전파 지연·lease 기간·시계 오차·갱신 주기·ACK timeout의 실제 수치는 아직 확정하지 않는다. Simulator에서는 짧은 명시적 fixture로 단절/만료/경합을 시험한다. 개발 fixture를 운영 기본값으로 사용하지 않는다. 외부 요구가 철회 요청 순간 즉시 전역 차단이라면 별도의 중앙 승인 게이트 또는 기관 차단을 포함한 구조 변경 검토가 필요하다.

### 4.3 작업별 제한

| 작업 | 계약 철회/MID 신규 결제 중지 시 권장 동작 |
|---|---|
| 신규 승인 | 차단 |
| 기존 승인 결과 조회·UNKNOWN 복구 | 현재 소유권과 별도 조회 권한으로 허용 |
| 기존 카드 취소 | 원 거래·반환 권한·원 경로 조건으로 처리, 신규 승인 권리와 분리 |
| 계좌환불 | 반환 권한·예약·수취인·재원·송금 통제를 별도 검사 |
| 미매입 거래 처리 | 이미 발생한 거래의 의무 및 기관 규약에 따라 처리 |
| 정산 계산·대사 | 기존 사실 처리 지속 |
| 가맹점 지급 | 채무는 보존하고 위험/법적/계좌 사유에 따라 지급 보류 여부 판정 |

폐기된 API 키를 계속 허용하는 뜻은 아니다. 기존 거래 처리도 유효한 별도 Credential/운영 권한이 필요하다. 전면 잠금과 신규 결제 중지를 분리한다.

## 5. 기관 연동 계약

### 5.1 업무와 전송 방식 분리

최초 가상 연동은 아래로 시작한다. 이는 사용자 제시 시나리오이며 모든 실제 VAN의 통신 방식이 동일하다는 주장이 아니다.

| 업무 | 소유 플랫폼 | 최초 가상 Adapter | 확장 가능 방식 |
|---|---|---|---|
| 카드 승인·취소·결과 조회 | PAYMENT | TCP 소켓 | TCP/TLS, HTTPS 등 |
| 승인/취소 매입 제출·결과 수신 | FINANCIAL | SFTP 파일 | HTTPS, 소켓, 다른 파일 채널 |
| 기관→PG 입금내역 | FINANCIAL | 기관 결과/입금 파일 Simulator | 파일, API |
| 가맹점 지급·은행 결과 | FINANCIAL | 가상 은행 | 기관별 소켓/API/파일 |

Domain은 authorize/cancel/inquire/submitAcquisition/receiveAcquisitionOutcome 같은 업무 의도와 내부 결과만 다룬다. Socket/SFTP/SDK/기관 DTO는 Adapter에 한정한다. 기관 프로파일은 operation별 Adapter ID·프로토콜 버전·Capability·timeout·연결/파일 설정의 참조를 갖고 비밀 원문은 별도 Secret 저장소에 둔다.

같은 매입 Use Case가 SFTP Adapter나 API Adapter를 호출해도 결과 접수/처리/확정 상태의 의미는 유지한다. 금융 실행은 임의 스크립트가 아니라 검증된 Adapter registry에서 선택한다. 당시 기관/프로파일/프로토콜 버전은 Attempt/Submission에 보존한다.

### 5.2 가상 기관 계약부터 고정

- ProviderContractVersion과 operation별 요청/응답/조회/통보/파일 schema를 만든다. 이는 가상 규격이며 실제 VAN 규격을 추측한 것이 아니다.
- namespace는 기관 + 환경 + 기관 계약계정 + operation + 요청 ID 범위로 정의한다. 동일 ID·동일 payload는 기존 결과를 조회/반환하고 다른 payload는 충돌로 거절하는 가상 기관을 기본으로 한다.
- 요청 ID 재사용과 조회 보존기간, 동일 ID 재전송 가능 여부를 Capability로 표시한다. 해당 기능 없는 가상 기관 프로파일도 추가해 안전 차단을 시험한다.
- 결과는 APPROVED/DECLINED, 확정 무효과 기술 실패, PENDING, UNKNOWN, 조회의 NOT_FOUND를 구별한다. NOT_FOUND는 설정된 기관 확정성 규칙 없이는 실패가 아니다.
- 요청 ID와 ProviderTransactionId, 승인번호, 원 승인 참조, 금액·통화, 기관 거래일·업무일, 응답 코드/증거를 보존한다. 기관 승인번호를 전역 UNIQUE로 가정하지 않는다.
- 성공 응답·통보·조회·대사 결과의 중복/상충 처리 규칙을 명시한다. 먼저 온 응답이나 마지막 응답을 무조건 정답으로 하지 않는다.
- timeout·rate limit·회로차단·최대 동시성·조회 예산은 operation별 설정이다. read timeout을 승인 거절로 해석하지 않는다.

### 5.3 소켓 승인 처리

1. 주문/승인 점유·Attempt·기관 요청 ID·Route/권리 버전 영속화 후 커밋한다.
2. 전송 게이트에서 현재 차단/lease 상태를 확인하고 실행 의도를 기록한다. 전송 여부를 증명할 수 없는 종료 구간은 보수적으로 UNKNOWN으로 복구한다.
3. DB TX 밖에서 연결/전문 송신/응답 수신을 수행한다.
4. 응답을 요청에 연결하고 금액·통화·원 참조·무결성을 검증한다. 원본 증거는 민감정보 보호 하에 참조한다.
5. PAYMENT 로컬 TX에서 최종 결과·금융 효과·요청 결과·Outbox를 반영한다. 실패하면 원 Attempt로 결과 조회한다.

TCP stream을 한 번의 read로 전문 하나라고 가정하지 않는다. 길이/프레이밍·부분 read/write·복수 전문·동시 요청의 응답 상관관계·재연결을 계약화한다. 라이브러리 write 성공은 기관 업무 접수/승인 성공이 아니다. connect/read/전체 deadline을 구분하고 기관이 지원하는 TLS/전문 인증을 적용한다. 소켓이 끊겨도 이미 성공한 승인 가능성을 남긴다.

### 5.4 SFTP 매입 처리

1. 확정 PAYMENT 금융 사실의 FINANCIAL Projection으로 매입 대상을 선택한다. 원 SALE 결과 불명확이면 취소 매입은 HOLD한다.
2. Acquisition과 별도로 Submission·파일 membership·업무일·회차·건수·총액·checksum·프로토콜 버전·재시작 checkpoint를 영속화한다.
3. 재시작해도 동일 Submission의 확정된 파일 bytes/hash를 유지한다. 필요하면 staging 후 seal한다. 운영 중 정책 변경으로 재생성한 다른 내용에 같은 ID를 사용하지 않는다.
4. SFTP host key와 서버 신원을 검증하고 기관이 약정한 임시명→rename 또는 완료 marker 방식으로 게시한다. 해당 방식의 지원/원자성을 실제 기관에 확인한다.
5. 업로드 성공, 기관 수신 ACK, 레코드별 매입 ACCEPTED는 서로 다른 상태다. 전송 완료만으로 매입/입금/정산 완료로 처리하지 않는다.
6. 결과 파일은 staging에 내려받아 형식·기관·업무일·참조·건수·총액·hash를 검증한다. 같은 파일 ID·같은 내용은 중복, 같은 ID·다른 내용은 격리한다.
7. 대량 파일은 레코드/명시된 원자 단위로 멱등 반영하고 checkpoint로 재개한다. 파일 전체 파싱/전송 동안 DB TX를 유지하지 않는다.
8. 누락·부분 처리·중복 결과·재수신을 대사한다. 접수 불명확 상태에서 새 ID로 무조건 재제출하지 않는다. 수정 파일은 원 제출 참조를 가진 새 버전/절차를 따른다.

### 5.5 Simulator 요구

Simulator는 PG 프로세스와 별도 프로세스·영속 저장소를 갖는다. PG 재시작/DB rollback으로 가상 기관의 이미 발생한 승인·입금·송금이 사라지지 않아야 한다.

- 가상 VAN TCP 서버: 승인/거절/취소/조회, 부분 전문/지연/끊김/중복/성공 후 응답 유실.
- 가상 SFTP 서버와 기관 Worker: 업로드 수신, 접수 ACK, 레코드별 ACCEPTED/REJECTED, 결과 파일 생성, 일부 결과 지연/파일 중복·상충.
- 가상 자금/은행 원장: 기관 입금과 가맹점 지급. 매입 ACCEPTED와 실제 입금을 다른 시점/사건으로 만든다.
- 결정 가능한 시나리오·seed·가상 시계·장애 주입을 지원한다. 정상뿐 아니라 결과 조회 지연/불가 및 기관 멱등 미지원 프로파일도 시험한다.
- SAMPLE/SIMULATOR endpoint·키·계정만 사용하고 운영기관 송신은 네트워크와 설정에서 차단한다. 가맹점 TEST/LIVE와 실행 backend SIMULATOR/REAL은 별도 축으로 둔다. 초기에는 어느 논리 환경도 실제 기관으로 나가지 않는다.
- 민감한 실제 카드/계좌 대신 가상 참조를 사용한다. 운영 키/실제 카드정보를 테스트 fixture로 가져오지 않는다.

### 5.6 검증·전환

도메인 시험 → 실제 DB 동시성/원자성 → TCP/SFTP 프로토콜 계약 → 전체 승인·취소·매입·입금·정산·지급·대사 → 장애·복원 시험 순으로 검증한다.

가상 기관으로 통과한 결과는 내부 정합성과 가상 규약의 증거다. 실제 전환 시 실제 전문 매핑·인증서·host key·보안·조회/중복 의미·기관 인증 시험을 별도 Gate로 수행한다. timeout/ID/파일 규약을 실제 값으로 다시 검증하고 Adapter만 교체해도 모든 업무 가정이 그대로 성립한다고 단정하지 않는다.

## 참고
