# PayCore 사업자 기본정보 관리 — 업무 정의 및 정책서

- 문서 ID: PC-BIZ-POL-001
- 버전: v1.1 (개발 착수 기준 초안)
- 작성 기준일: 2026-11-17
- 대상: PayCore 신규 1차 PG / 사업자 기본정보 관리
- 근거: 레거시 ‘신규계약 신규등록’ 화면 및 사업자·KYB·계약 분리 검토안
- 표기: **[확정]** 사용자 결정 / **[제안]** 설계 권장 / **[TBD]** 후속 결정

## 1. 확정 전제 및 범위

1. **[확정] 기존 IMS와 신규 PayCore는 프로젝트·DB·기능 연계가 전혀 없다.** 레거시 IMS 코드를 마이그레이션하거나 재사용한다는 전제를 두지 않는다. 레거시 화면은 항목 비교를 위한 참고자료일 뿐이다.
2. **[확정] PayCore에서 사업자 등록은 계약·가맹점·결제 개통으로 이어지는 독립된 초기 업무이다.** 등록 자체로 계약·MID·서비스·정산데이터를 생성하지 않는다.
3. **[확정] 1차는 Business 1건에 BusinessRegistration 1건을 생성한다.** 모델은 확장 가능하게 설계할 수 있으나, 본점·지점 관계 생성, 동일 법적 주체 판정, 사업자 병합은 이번 개발에서 구현하지 않는다.
4. **[확정] 본점·지점이 동일 법적 주체인지 판단하는 근거와 판정 규칙은 후속 정책으로 미룬다.** 법인등록번호 일치만으로 자동 연결·병합하지 않는다.
5. **[확정] AML/KYB 고객확인과 심사 요청·승인 워크플로는 후속 연동 대상이다.** 이번에는 심사 데이터 수집·심사 요청 API·심사 승인 로직을 만들지 않는다. 향후 연동을 고려한 도메인 분리만 유지한다.
6. **[확정] 1차 사용자 대상은 국내 개인사업자와 국내 법인사업자이다.** 비영리·해외 법인은 확장 대상(TBD).

## 2. 업무 목적

사업자를 PayCore에서 한 번 등록하고 조회·수정·중복확인할 수 있는 독립적 기준정보를 구축한다. 사업자 식별, 외부 사업자 검증, 고객확인, 계약 심사, MID 발급을 각기 다른 책임으로 분리한다.

레거시의 ‘신규계약 신규등록’에는 사업자 기본정보, 고객확인, 영업관리, 계약·수수료·담보가 혼재했다. **신규 PayCore에서 화면을 복제하지 않는다.**

## 3. 업무 도메인

| 개념 | 정의 | 1차 처리 |
|---|---|---|
| Business | PayCore 내부 사업자 주체. `businessId`로 식별 | 신규 생성·조회·수정 |
| BusinessRegistration | 사업자번호·상호·개업일 등 등록정보 | Business당 1개 생성 |
| BusinessRepresentative | 현재·과거 대표자 관계 | 복수 대표자 입력·변경 이력 |
| BusinessContact | 사업자 측 등록·업무 담당자 | 1명 이상 등록 |
| BusinessAddress | 사업장 주소와 선택적 실제사업장 | 등록·수정 |
| BusinessCategory | 업태·종목 | 각각 복수 지원 |
| BusinessDocument | 사업자등록증 등 증빙 | 선택 첨부, 향후 심사에 참조 |
| BusinessVerification | 중복조회와 분리된 진위·상태 확인 결과 | 인터페이스/이력 설계, 실제 연동은 의존성에 따라 단계화 |
| BusinessAudit | 변경사유·작업자·변경 전후 이력 | 1차 필수 |
| Merchant / KYB / Contract / MID / FeePolicy / SettlementPolicy | 별도 후속 도메인 | 이번 구현 제외 |

**중요:** Business 식별자와 사업자등록번호를 동일하게 취급하지 않는다. 1차 생성 관계는 1:1이지만 관계 확장과 연결 판단은 후속 범위다. 사업자번호별 유일성은 유지한다.

## 4. 업무 흐름

`사업자 목록 → 신규등록 → 중복확인 → 기본정보 입력 → 임시저장(DRAFT) 또는 등록 완료(REGISTERED) → 상세조회·수정`

- `DRAFT`: 최소 입력만으로 임시저장 가능. 미입력 항목이 있어도 허용하되 입력된 필드의 형식은 검사한다.
- `REGISTERED`: 단계별 필수 입력의 충족 및 DB 중복 검사가 완료된 상태. **진위확인, AML/KYB 승인 또는 계약 승인이라는 뜻이 아니다.**
- `INACTIVE`: 내부 관리상 비활성화 상태. 처리 권한과 사유 필수; 재활성화 정책은 TBD.

후속 예정 흐름(이번 개발에서 구현하지 않음): `사업자 등록 → 진위/영업상태 확인 → Merchant 신청 → AML/KYB·서비스 심사 → 계약 → MID 발급 → 결제/정산 설정 → 개통`.

## 5. 화면 항목과 필수 시점

| 분류 | 항목 | DRAFT | REGISTERED | 정책 및 비고 |
|---|---|---|---|---|
| 기본 | 사업체 구분 | 선택 | 필수 | 개인 / 법인 |
| 기본 | 상호(한글) | 선택 | 필수 | 사업자등록증 기준, 브랜드명과 구분 |
| 기본 | 사업자번호 | 선택 | 필수 | 10자리 숫자 정규화, 유일성 검사 |
| 기본 | 법인등록번호 | 선택 | 법인 필수 | 13자리 형식, 개별 관리 |
| 기본 | 대표자명 | 선택 | 1명 이상 필수 | 복수 대표자/공동·각자 유형 지원 |
| 기본 | 개업일자 | 선택 | 필수 | 법인 설립일과 구분 |
| 기본 | 업태 | 선택 | 1개 이상 | 복수 입력 가능 |
| 기본 | 종목 | 선택 | 1개 이상 | 복수 입력 가능 |
| 주소 | 사업장 주소 | 선택 | 필수 | 우편번호·기본주소·상세주소 |
| 주소 | 실사업장 주소 | 선택 | 조건부 | 다른 경우에만 입력 |
| 연락 | 사업체 연락처 | 선택 | 필수 | 유선전화만 강제하지 않음 |
| 연락 | 사업체 이메일 | 선택 | 선택 | 담당자 이메일과 중복 입력 강제 금지 |
| 담당 | 등록 담당자 | 선택 | 1명 이상 필수 | 이름·이메일·연락처 필수 |
| 기본 | 영문 상호 | 선택 | 선택 | 해외 연동 필요 시 사용 |
| 기본 | 등록국가 | KR | KR | 1차 국내만 지원 |
| 파일 | 사업자등록증 | 선택 | 선택 | 후속 심사 요청 시 확보, 이번에는 심사 요청 기능 없음 |

**[제안]** DRAFT는 서버가 ID를 할당한 뒤 부분 입력 형태로 저장한다. DRAFT 최초 생성의 최소 입력 항목과 만료·삭제정책은 구현 전 결정(TBD)하되, 식별번호가 존재할 때는 중복 생성을 허용하지 않는다.

## 6. 업무별 핵심 정책

### POL-001 사업자 중복
- 내부 등록 여부 확인과 국세청 진위확인 및 영업상태조회는 **서로 다른 기능**이다.
- 사업자번호 입력 후 내부 중복 조회를 제공하며, 저장 시 서버와 DB가 중복을 재검증한다.
- 동일 사업자번호는 새로운 활성 등록정보로 중복 생성하지 않고 기존 Business 조회를 안내한다.
- 동시 요청에서도 DB 제약으로 동일 번호의 중복 커밋을 방지한다.
- 이미 등록된 사업자에 계약·Merchant 연결은 향후 별도 기능에서 수행한다.

### POL-002 사업자 상태
- 내부 상태는 `DRAFT / REGISTERED / INACTIVE`.
- 진위확인 결과(`NOT_CHECKED / VERIFIED / MISMATCH / FAILED`)와 영업상태(정상·휴업·폐업·미확인)는 별도 속성/이력이다.
- 외부기관 통신 실패를 검증 성공으로 간주하지 않는다.
- 1차에는 심사 요청·승인·반려 상태를 추가하지 않는다.

### POL-003 대표자·담당자
- 등록 완료 시 현재 유효한 대표자 최소 1명, 등록 담당자 최소 1명을 요구한다.
- 공동·각자대표 등 복수 대표자를 저장할 수 있도록 설계한다.
- 대표자 교체는 과거 관계를 종료하고 새 관계를 추가하며 변경 이력을 남긴다.
- 사업자 측 담당자와 내부 PayCore 영업/계약/운영 담당자는 다른 개념이다.
- 생년월일, 대표자 국적, 실제소유자 정보 등 AML/KYB 자료는 **이번 최초 등록 화면에서 받지 않는다.** 후속 연동 시 해당 단계에서 필요성을 검증해 수집한다.

### POL-004 수정·감사
- 연락처·이메일·주소 등 일반정보는 권한 있는 관리자가 수정한다.
- 사업자번호·법인번호·대표자·상호·개업일자 등 중요정보 변경 시 사유 및 변경 전후 이력이 필수다.
- 등록 후 사업자번호 변경을 단순 UPDATE로 처리하지 않으며, 정정/새 사업자 판단정책을 TBD로 남긴다.
- 갱신 충돌은 버전 컬럼(낙관적 잠금 등)을 사용해 방지한다.

### POL-005 증빙 및 외부 검증
- 사업자등록증은 임시저장·등록 완료 시 선택이고, 추후 심사 요청 시 필요한 증빙으로 정의한다.
- 파일 업로드 시 종류·크기·서명/MIME·악성파일 등 보안 검증과 접근권한 검증을 수행한다.
- 국세청 진위·영업상태 API의 실제 연결 여부·호출자격·오류 대응은 별도 연동 결정(TBD). 연동 전에는 검증 완료로 표시하지 않는다.

### POL-006 삭제·운영
- 등록 완료 사업자의 물리삭제를 제공하지 않고 비활성화를 원칙으로 한다.
- 임시저장 정리 및 개인정보 보관·파기 기준은 별도 확정(TBD).
- `INACTIVE`는 내부 기준정보 관리 상태이며 결제·정산 정지로 연결하지 않는다(후속 연계 정책 필요).

## 7. 범위 밖으로 분리할 레거시 항목

| 기존 항목 | 후속 책임 도메인 |
|---|---|
| 대표자 생년월일·국적·지분, 실제소유자, 상장/비영리/가상자산 취급, 자본금 | AML/KYB·위험평가 |
| 접수일·접수경로·상담중·통화이력 | 이용신청·영업관리 |

| 계약·정산·기술담당 역할, 세금계산서 이메일 | 연락 담당자/계약/청구 설정 |
| 등록비·연운영비·계약일·계약서 | Contract |
| 신청서비스·서비스수수료·영중소 등급 | MerchantService·FeePolicy |

| 정산계좌·정산주기·VAN·카드사 가맹점번호 | 지급/정산/결제수단 개통 |

## 8. 권한·보안·감사

- 조회/등록/수정/비활성화/파일다운로드 권한을 분리한다. 세부 역할은 PayCore 자체 권한체계에 매핑한다.
- 요청자·수정자·시각·변경사유·변경항목을 저장하고 중요한 식별정보는 로그에서 마스킹한다.
- 프론트 버튼 숨김으로 권한을 대체하지 않고 서버에서 인가한다.
- 파일 바이너리는 공개 URL을 통한 직접 노출을 금지한다.
- 등록·변경 이력이 실제 거래·심사 프로세스에 연결될 때 과거 시점 정보를 추적할 수 있도록 한다.

## 9. 업무 수용 기준

1. 개인·법인 사업자 등록을 지원하며 법인번호를 조건부 필수로 검증한다.
2. 임시저장과 등록 완료의 필수값 기준이 다르다.
3. 동일 사업자번호 중복 등록을 DB 수준에서 방지한다.
4. 복수 대표자, 복수 업태·종목, 담당자 입력을 지원한다.
5. 기본정보 조회·수정·변경사유/감사이력을 제공한다.
6. 외부 검증이 실행되지 않은 상태를 정확하게 미검증으로 표시한다.
7. 사업자 등록으로 KYB·계약·MID·정산 데이터가 생성되지 않는다.
8. 기존 IMS와의 연동·이관 로직이 존재하지 않는다.
