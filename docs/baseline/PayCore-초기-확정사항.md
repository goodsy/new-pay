# PayCore 초기 확정사항

기록일: 2026-10-03 KST. 이번 대화의 사용자 결정 기록이며 첨부 ZIP 원문은 수정하지 않는다.

## 출시 범위

- 직접 PG인 1차 PG를 먼저 구축한다.
- 최초 결제수단은 국내 신용카드 결제다.
- 이후 다른 결제수단과 해외결제를 추가할 수 있도록 경계를 설계한다.
- 지원 통화, 일시불/할부, 체크카드, 최초 기관, 자금/정산 세부 정책은 별도 확정 대상이다.

## 확정: 가맹점·계약·MID 기본 관계

사용자가 이번 대화에서 위 권장 관계를 확정하도록 요청했다. 아래 기본 관계를 구현 기준으로 사용한다.

- 하나의 Business가 복수 Merchant를 가질 수 있다.
- Merchant는 복수 MerchantSite를 가질 수 있다.
- Merchant는 최초 Default MID 하나를 발급받고 필요 시 추가 MID를 발급받는다.
- MID는 발급 근거가 되는 계약 서비스 하나를 명시한다.
- MID와 Site는 계약의 허용 범위 안에서 연결하며 관계 이력을 보존한다.
- Default는 기본 계정 선택 용도다. 계약·권한·정산 조건을 자동 상속하지 않는다.

후속 첨부 채택으로 MID–Site는 Assignment Entity로 N:M을 수용하며 기본 1:1, 조건부 복수 Site 공유로 확정됐다. Production MID의 최초 Site 연결을 요구한다. 상세 기준은 아래 도메인 구조 확정본을 따른다. 계약 갱신 시 MID 근거 변경, Default 교체/종료, 추가 MID 발급 승인 및 정산 경계의 잔여 규칙은 별도 구체화한다. 동일 사업자의 모든 브랜드를 한 Merchant로 강제하지 않는다.

계약은 당사자·Scope·Revision과 서비스 권리를 구분한다. 초기 Scope는 Merchant 또는 MerchantSite이며 GID에 계약·수수료·정산·접근 권한을 자동 상속하지 않는다. MID는 BusinessId나 카드사 가맹점번호와 구분한다. 발급 시점의 계약 서비스와 근거 Revision을 보존한다.

기존 승인 방향도 유지한다. 계약 승인 후 효력 시작 전 MID 선발급은 가능하지만 실제 결제는 계약 효력·개통·운영·인증·경로 조건이 충족되어야 한다. 계약 철회 시 발급 이력을 보존하며 해당 계약의 신규 결제를 차단한다. 재승인만으로 자동 재활성화하지 않는다. 최초 Default의 MID·지정·성공 요청 결과는 같은 MASTER 로컬 TX로 저장하며 다른 키의 동시 최초 발급은 하나만 성공한다.

## 확정: 결제 시도 규칙

사용자는 권장안을 검토한 뒤 “이안으로 해줘”로 채택했다. [결제 시도 규칙 확정본](PayCore-결제시도-규칙-권장안.md)을 구현 기준으로 사용한다.

- 주문 키는 환경 + MID + 가맹점 주문번호다.
- 주문 하나에 여러 Payment 이력은 허용하되 REQUESTED를 포함한 활성 Payment는 하나다.
- Payment당 논리 Authorization 하나, 동시 기관 승인 실행 하나를 허용한다.
- 같은 내용의 활성 주문 중복 요청은 기존 시도로 수렴하고 다른 내용은 충돌로 거절한다.
- 확정 거절/무효과 실패·안전한 만료 이후 새 Payment를 허용한다. AUTHORIZING/UNKNOWN에서는 추가 승인 없이 결과 확인을 우선한다.
- 승인 성공 주문은 전액 취소/환불 후에도 다시 승인하지 않는다. 재구매 및 금액·통화·결제 대상 변경은 새 주문번호를 사용한다.
- 부분 승인·다중 수단 분할 결제는 초기 미지원이다.
- 상세 만료·멱등·기관 재시도·동시성 및 필수 테스트는 연결된 확정본을 따른다. 차단 전파·LIVE 준비의 기본 규칙은 아래 4번 확정본을 따른다. 기관별 실규약·운영 수치·물리 DB 설계는 별도 결정/검증 대상이다.

## 확정: 가상 외부기관으로 실서비스 구조 개발

실서비스를 위한 시스템을 구축하되 현재 기관 연동은 가상 기관으로 구현한다. 사용자가 제시한 최초 시나리오는 VAN 승인 소켓통신과 매입 SFTP다. 업무 처리와 통신 방식은 분리하며 기관/operation별 Adapter를 교체할 수 있게 한다. 실제 기관의 규약·인증 완료를 가상 연동 성공으로 대체하지 않는다.

## 확정: 4. 실제 결제 허용 조건

사용자가 4·5번 권장안을 채택했다. [실제 결제 허용 조건·기관 연동 계약 확정본](PayCore-결제허용-기관연동-권장안.md)을 구현 기준으로 사용한다.

- 인증·가맹점/MID·계약 효력/권리·Site Scope·개통·주문/금액/인증·정책 버전·기관 경로·중복 제어·안전 조건을 모두 충족해야 신규 승인을 허용한다.
- PAYMENT 승인 Use Case가 최종 판정하며 근거 버전을 보존한다. MID 발급만으로 결제를 허용하지 않는다.
- 로컬 Snapshot과 만료 있는 권리 lease를 사용한다. 필수 정보 누락/만료 시 신규 승인 차단, 긴급 차단 우선 전파 및 ACK/lease 만료/격리로 전역 효력 확인.
- 계약 철회/키 폐기와 진행 중 외부 승인을 구분한다. 기존 승인 결과 복구, 취소·대사·정산 의무는 유효한 별도 권한으로 처리한다.
- 전파 지연·lease 기간 등 운영 수치, 철회 중 승인 성공의 사후 처리는 본문에 명시된 별도 정책 대상이다.

## 확정: 5. 기관 연동 계약

- 승인/취소/조회는 PAYMENT, 매입/입금/지급/대사는 FINANCIAL 소유로 처리한다.
- 최초 가상 VAN은 TCP 소켓, 매입은 SFTP로 구현한다. 업무 Port와 전송 Adapter를 분리하고 기관/operation별 검증된 Adapter를 선택한다.
- 가상 기관의 버전 있는 규격·요청 ID namespace·멱등/조회 Capability·결과 의미·파일/전문 및 장애 계약을 먼저 정의한다.
- 전송 성공·파일 업로드·접수 ACK·매입 확정·입금은 독립 상태다. 불명확 전송 결과를 무조건 실패/재요청으로 처리하지 않는다.
- 별도 프로세스/영속 저장소의 가상 VAN·매입기관·은행을 사용하고 PG 재시작에도 기관 금융 사실을 유지한다.
- 실제 기관 전환은 실제 규약·보안·인증 시험을 별도 검증한다. 가상 기관 성공을 실서비스 인증으로 간주하지 않는다.

1~5번의 기본 방향과 위 상세 규칙은 확정됐지만 지원 통화·일시불/할부/체크카드·고객 인증 흐름, 관계의 잔여 세부, 이벤트/물리 스키마, 수수료·정산·자금 통제 정책과 운영 수치는 별도 구체화 대상이다. 코드 구현 또는 운영 준비 완료를 뜻하지 않는다.

## 확정: 입금 후 지급·선지급 모두 지원

사용자 결정: “입금후 정산과 선지급을 기준정보 설정에 따라 둘다 허용 가능”. 기관 입금 후 지급하는 방식과 기관 입금 전 선지급하는 방식을 모두 지원하고, 기준정보/버전 있는 정책 설정으로 선택한다. 앞서 assistant가 권장한 초기 선지급 미지원은 채택하지 않는다.

정산 계산·지급채무 확정·지급 실행·기관 입금은 별도 상태로 유지한다. 입금 전 선지급 지원이 승인 성공만으로 무조건 정산/지급 가능하다는 뜻은 아니다. 지급 기준일·선지급 적격 거래·한도·재원·보류·회수·승인 권한은 별도 상세 정책 대상이다.

두 모드와 자금 통제의 상세 권장안은 [정산·지급 방식 설계](PayCore-정산지급방식-확정과-상세권장안.md)를 참조한다. 정책 모드 지원은 확정이며 구체적인 한도/해제 기준을 자동 확정하지 않는다.

### 확정: 선지급 기준

사용자가 매입 확정·매입 요청·승인 완료 거래에 대한 선지급을 결정했다. 세 기준을 모두 지원하고 선지급 정책에 적용 기준을 연결한다. 매입 확정 거래만 초기 지원하자는 직전 권고는 채택하지 않는다.

동일 거래의 단계 진행이 별도 선지급을 반복 발생시키지 않도록 채무/지급 업무키를 유지한다. 선지급 기준과 정산 주기·예정 지급일·한도·재원 조건을 구별한다. 매입 거절/UNKNOWN의 보류·회수 처리 및 정책 적용 시점은 별도 확정 대상이다.

매입 요청 인정 시점은 사용자가 “외부기관에 전송완료”로 확정했다. 내부 요청 저장/파일 생성만으로는 충족되지 않고, 기관 접수 ACK나 거래별 매입 확정은 선행 요구가 아니다. 전송 완료 근거를 영속화하고 파일 기반에서는 해당 파일에 실제 포함된 거래에만 연결한다. 완료 여부가 불명확하면 확인 전까지 전송 완료로 인정하지 않는다. Adapter별 전송/게시 검증 방법은 상세 구현 계약으로 구체화한다.

## 확정: 수수료·정산 날짜 및 자동 대사 방향

사용자 결정에 따라 수수료 적용 날짜는 승인일자로 한다. 취소 시 원승인 거래의 승인일자에 적용한 수수료/VAT 정책 근거를 참조한다. 원 계산 버전/입력을 보존하며 취소일의 최신 정책으로 원 수수료를 다시 계산하지 않는다. 후속 Settlement Control Policy v0.1 채택으로 VAT 반올림은 버전 있는 기준정보에서 선택하도록 확정됐다. 실제 반올림 방식·단위·세율 및 원승인 수수료 반환 비율/고정비 반환 여부의 값은 별도 설정 대상이다.

정산 적용 날짜는 거래일(승인/취소 각 거래의 날짜)이다. 영업일 기준으로 처리하며 거래일이 비영업일이면 그다음 영업일을 기준일로 사용한다. 휴일 관리를 포함한다. 취소 수수료의 원승인 정책 참조와 취소 정산의 취소 거래일은 구분한다. 시간대·영업일 캘린더 범위·D+N/마감·소급 휴일 변경은 별도 상세화한다.

대사 차이에 자동 보정 프로세스를 적용하고 위험이 있으면 차단하는 방향을 채택한다. 자동화 범위·증거·승인 규칙·중단/해제 조건과 원장 정정 방식은 [통제·관계·대사 상세 대안](PayCore-금융통제-관계-자동대사-대안.md)의 추가 검토 대상이다. 차이 발견만으로 금액을 덮어쓰거나 기관 금융 요청을 재실행하는 정책을 승인한 것은 아니다.

## 확정: Settlement Control Policy v0.1

사용자가 첨부한 정산·선지급·대사 권장안을 “으로 해줘”로 채택했다. 현행 기준은 [Settlement Control Policy v0.1 확정본](PayCore-Settlement-Control-Policy-v0.1.md)이다. 이전 금융통제 대안과 충돌하는 제안은 이 확정본을 우선한다.

- 수수료/VAT는 원승인일 정책 Snapshot과 원 계산을 참조하고 계산·반올림·세율은 버전 있는 기준정보로 관리한다. 반올림 방식 확인 질문은 기준정보 선택으로 해소됐다. 실제 정책값은 별도 설정한다.
- 정산 거래일은 승인일/취소일/Refund 완료일이며 비영업일은 다음 영업일로 보정한다. transactionDate/baseDate/dueDate를 구분하고 versioned Calendar의 계산 결과를 보존한다.
- 별도 Financing Domain 없이 확정 Settlement/Payable의 Early Release와 Eligibility로 조기 지급한다. 기존 입금 후/선지급 모드와 세 거래단계 기준은 유지하고 일정·재원 조건은 분리한다.
- Advance-only/All-payout Hold, SettlementHold/PayoutHold를 구분한다.
- 대사 Case→위험판정→자동 Recovery/제한적 Adjustment/Manual Review/Block을 적용한다. LOW는 정책 허용 범위의 자동화, MEDIUM은 수동 검토, HIGH/CRITICAL은 Hold+수동 검토가 기본이다.
- 자동 보정은 멱등·한도·kill switch·감사를 갖추고 재대사 MATCH 후에만 Case를 RESOLVED로 처리한다. 확정 원장 UPDATE가 아닌 별도 Adjustment를 사용한다.
- 재지급·고액 조정·Critical 해결·강제 Hold 해제·선지급 예외는 2인 승인 구조를 수용한다. 정책은 exactly one applicable policy로 해석하고 모호함은 실패한다.

해당 첨부에 포함되지 않은 관계 대안은 후속 도메인 구조 첨부에서 일부 확정됐다. 최초 통화/카드 범위의 추가안, 실제 운영 수치/회수 정책 및 실제 구현·검증은 자동 확정하지 않는다.

## 확정: v0.1 도메인 구조·정책 Seed·MID–Site

사용자의 첨부 요청에 따라 [도메인 구조·정책 Seed·MID–Site 확정본](PayCore-v0.1-도메인구조-Seed-MID-Site-확정.md)을 채택한다.

- 구조·계산 기준을 확정하고 실제 요율·정산주기·한도는 버전 있는 기준정보 값으로 분리한다. 예시 수치는 DEMO DATA이며 운영값이 아니다.
- 최초 SettlementCycle 엔진은 DAILY_OFFSET(D+N 영업일). D+2는 Demo Seed다. Weekly/Monthly/SemiMonthly는 후속 확장한다.
- Advance/Payout/AutoCorrection 한도 모델을 분리한다. 최초 Advance는 enabled/건당/일 금액, Correction은 건당/일 금액/일 건수 한도를 지원한다.
- MID–Site는 MerchantAccountSiteAssignment로 N:M을 수용한다. 기본은 1:1, 복수 Site 공유는 동일 Merchant·Agreement·개통 적용·정산 정책·기관 심사 허용 조건을 충족해야 한다.
- Production MID는 최초 Site 연결을 요구한다. 최초 Default 발급에서 SiteAssignment도 같은 MASTER TX에 저장한다. 선발급은 유지하되 실제 승인에는 계약 효력·개통 등 준비 조건을 요구한다.
- 다른 Merchant 간 MID 공유 금지. 최초 PRIMARY/추가 ADDITIONAL 역할 및 EffectivePeriod/상태·변경 이력을 관리한다. 거래 당시 Site와 근거는 보존한다.
- Activation은 최초 MID 단위부터 구현하되 Site Scope 확장 경계를 둔다. Site 공유 시 개통·기관 심사 근거가 해당 Site에 적용되는지 검증한다.
- 운영값은 새 Version/적용 기간으로 변경하고 과거 거래의 Snapshot을 바꾸지 않는다. Demo Seed는 Simulator 전용이며 운영 기본값으로 자동 설치하지 않는다.

관계의 기간 경합/PRIMARY 교체·Default 생명주기·구체 운영 값·최초 카드 범위 추가안 및 실행 코드/검증은 후속 작업이다.

## 토스페이먼츠 공개 문서와 비교

최초 통화·카드 범위·할부·고객 인증 흐름의 추가 권장안은 [최초 구현 범위 권장안](PayCore-최초구현범위-권장안.md)에 기록한다. 해당 추가 범위는 아직 사용자 확정 전이며 기존 신용카드 우선 결정을 체크카드 포함으로 자동 변경하지 않는다.

토스페이먼츠는 하나의 상점에 여러 MID가 발급될 수 있다고 설명한다. 서비스별 MID/API 개별 연동 키와 TEST/LIVE 키 구분이 공개되어 있다. 이는 PayCore의 가맹점과 MID 분리 및 서비스별 운영 경계와 유사한 외부 동작이다.

- [상점관리자](https://docs.tosspayments.com/resources/glossary/dashboard)
- [API 키](https://docs.tosspayments.com/reference/using-api/api-keys)
- [FAQ](https://docs.tosspayments.com/resources/faq)

이 자료는 토스페이먼츠 내부의 Business/Merchant/Site 모델, Agreement-MID cardinality, Default MID 정책, DB/트랜잭션 구조를 증명하지 않는다. PayCore 정책의 근거는 사용자 결정이며 타사의 내부 구조를 동일하다고 주장하지 않는다.
