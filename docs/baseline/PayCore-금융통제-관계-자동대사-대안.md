# PayCore 금융 통제·관계 세부·자동 대사 대안

2026-10-03 KST / 사용자 날짜·자동화 방향은 확정, 아래 상세 선택안은 제안

후속 상태: 사용자가 [Settlement Control Policy v0.1](PayCore-Settlement-Control-Policy-v0.1.md)과 [도메인 구조·Seed·관계 확정본](PayCore-v0.1-도메인구조-Seed-MID-Site-확정.md)을 채택했다. 정산·선지급·대사 및 관계의 현행 규칙은 두 확정본을 우선하고 이 문서는 대안 검토 이력으로 보존한다. 이 문서에서만 제시한 잔여 대안은 자동 채택하지 않는다.

## 1. 이번 결정과 잔여 구체화

| 항목 | 확정 방향 | 추가 결정 |
|---|---|---|
| 수수료 적용 | 승인일자 | 적용 timezone/기관일 의미, 실제 요율·계산 방식 |
| 취소 수수료/VAT 근거 | 원승인일 적용 정책 및 원 계산 참조 | VAT 반올림 방식/단위, 반환 비율·고정비 반환·마지막 잔액 |
| 정산 적용 | 승인/취소 각각의 거래일 | 마감, D+N, 첫날 포함 여부 |
| 영업일 기준 | 비영업 거래일은 다음 영업일 | 캘린더 소유, 은행/기관 차이, 특별영업일·소급 변경 |
| 대사 운영 | 차이 자동 보정 + 위험 시 차단 | 허용 유형/증거, 금액·건수·누적 예산, 중단/해제 |

수수료 정책 적용 날짜와 금융 사실 발생시각/정산 기준일을 분리한다. 1월 승인·2월 취소라면 취소 수수료 반환은 원승인 계산을 참조하고 취소 정산 반영은 2월 취소 거래일에 둔다. 거래일이 휴일이면 다음 영업일로 보정한다. 정산 반영일을 원승인일로 돌리지 않는다.

정책를 승인일로 찾더라도 같은 날 여러 정책 Revision이 가능하므로 효력 경계와 timezone을 정의하고 승인 때 선택한 정확한 버전을 보존한다. 원 정책이 없으면 현재 정책으로 대체하지 않고 보류한다. VAT 세율·면세/포함/별도 및 반올림 방식은 이 문서가 세법/계약 결론을 대신하지 않는다.

## 2. 선지급 통제 대안

| 대안 | 내용 | 평가 |
|---|---|---|
| A: MID 개별 한도 | MID마다 선지급 노출 한도와 지급 한도 | 단순하나 동일 사업자가 MID를 늘려 총노출을 우회할 위험 |
| B: 여러 범위 한도 동시 검사 | PG 전체 재원·기관 집중·사업 주체/가맹점 총노출·MID 한도 동시 적용 | 권장. 초기에는 정적인 승인 한도로 시작 가능 |
| C: 위험 기반 동적 한도 | B에 실적·취소율·입금 지연 등 자동 한도 조절 추가 | 후속 확장. 설명/검증/급변 통제 필요 |

권장 B의 구성:

- 건별/일별 지급 한도와 기관 미입금 선지급 노출 한도를 분리한다.
- 승인 완료/매입 전송 완료/매입 확정 기준마다 다른 한도·보류 조건을 설정할 수 있다. 승인 기준이라는 이유로 수치를 임의 확정하지 않는다.
- 가맹점/사업 주체 한도는 위험 집계 목적이며 GID나 Default의 권한/계약 자동 상속을 만들지 않는다. 다른 법적 주체의 자금을 자동 상계하지 않는다.
- PG가 선지급에 사용할 수 있는 확인된 재원만 사용한다. 은행잔액 전체와 사용 가능 재원을 동일시하지 않는다. 가맹점 채무·예약·보호/제한 자금·기존 실행을 구분한다.
- 선지급 미입금 노출, 기관 미수금, 은행 자금 예약은 다른 기록이다. 예를 들어 가맹점 지급액 97,000원과 기관 미수금 100,000원이 같지 않을 수 있으므로 하나의 잔액으로 합치지 않는다. 예시 금액은 정책값이 아니다.
- 지급 TX1에서 채무 Claim과 모든 적용 한도/재원 점유를 원자 처리한다. 잠금 순서를 고정한다. 초과/부족은 지급 보류로 표현한다.
- 기관 송금 UNKNOWN은 점유 유지. 명확한 무효과 실패만 재원/Claim을 정책에 따라 해제한다. 송금 성공은 자금 예약을 실제 지출로 전환하며 미입금 노출을 기관 입금까지 유지한다.
- 입금 배분·기관 순입금/차감 대사 후 노출을 해소한다. 단순 입금 파일 수신만으로 전액 해소하지 않는다.

지급 전 매입 거절/후발 취소/위험 정보가 오면 영향 거래 또는 지급 묶음을 보류하고 재산출한다. 지급 후에는 과거 지급을 지우지 않고 회수채권·다음 정산 차감·별도 조정 이력을 만든다. 회수/상계 Scope와 계약 근거는 별도 채택 대상이다. 취소/환불 예약 중인 금액이 신규 선지급에 포함되지 않도록 PAYMENT 반환 의도/예약 정보를 버전 있는 이벤트로 전달하는 계약이 필요하다.

차단은 선지급만 중지, 해당 기관 경로 중지, 거래/채무 지급 보류, 신규 승인 중지 등으로 구분한다. 재원 부족만으로 모든 신규 승인을 자동 중지하지 않는다. 운영상 더 넓은 중지는 별도 규칙과 효력 확인을 요구한다.

## 3. 관계 세부 대안

### MID–Site

| 대안 | 내용 | 평가 |
|---|---|---|
| A | MID 하나가 Site 하나만 사용 | 단순, 공유 운영에 추가 MID가 필요 |
| B | MID 하나가 복수 Site, Site는 복수 MID 사용 | Assignment N:M 권장. 명시 선택/기간/Scope 검증 필요 |
| C | 기술 모델은 B, 초기 운영을 Site별 전용 MID로 제한 | 복잡성 절충. 운영 제한 자체를 정책으로 관리 |

권장 B를 기본 모델로 하되 다음 불변조건을 적용한다.

- 동일 Merchant 소속이고 계약이 허용한 Site만 연결한다.
- Merchant 범위 계약은 허용된 복수 Site에 사용할 수 있다. Site 전용 계약의 MID는 다른 Site로 연결하지 않는다.
- 결제 요청은 MID와 Site를 명시하고 서버가 관계/기간/서비스를 확인한다. Merchant Default로 미지정 Site를 자동 우회하지 않는다.
- 동일 서비스에 복수 MID를 연결할 수 있어도 해당 결제는 MID 하나로 고정한다. 요청 중 다른 MID로 이동해 주문 중복 통제를 우회하지 않는다.
- Assignment는 유효기간·변경 버전·사유를 보존한다. 거래는 당시 Site/MID/Agreement 근거를 보존한다.
- N:M 연결 자체가 합산정산 허용은 아니다. 초기 정산/채무는 MID·수취인·통화 기준으로 구분하고 여러 MID 합산 지급은 별도 계약/정책으로 결정한다.

### Default·추가 MID·계약 갱신

권장안:

- Default는 발급 전/종료 후 0개, 발급된 운영 범위에서는 최대 1개다. 최초 하나를 만드는 기존 원자성 결정은 유지한다.
- 변경은 소유자 요청 + 권한/승인 + Merchant 단위 직렬화로 수행한다. 새 Default는 같은 Merchant의 유효 MID여야 한다. 기존 MID/거래는 보존한다.
- 종료된 Default의 다른 MID 자동 승격은 하지 않는다. 명시 변경을 요구한다.
- 추가 MID는 새 계약 서비스·Site 격리·기관/정산 운영 필요 등 근거와 승인 이력을 요구한다. 단순 정산주기 차이를 자동 발급 사유로 만들지 않는다.
- 같은 Agreement의 새 Revision/갱신은 재검증 후 MID를 유지할 수 있고 적용 기간/버전을 이력으로 남긴다. 다른 법적 주체/서비스 Agreement로 전용 MID를 조용히 재귀속하지 않는다. 신규 발급/명시 이관 절차가 필요하다.
- 계약 종료 후에도 기존 조회·취소·채무·대사 의무를 처리할 별도 유효 권한/경로를 유지한다.

## 4. 자동 대사·보정 대안

| 대안 | 내용 | 평가 |
|---|---|---|
| A: 관찰 자동화 | 차이 탐지/분류만 자동, 모든 해결 수동 | 보수적이나 운영 부담 큼 |
| B: 근거 기반 제한 자동 보정 | 정확한 원 거래 근거가 있는 복구 자동, 금액 변경/재전송/고위험은 차단·검토 | 초기 권장 |
| C: 정책 승인 기반 금액 조정 자동화 | B에 승인된 유형·금액·건수·누적 한도 내 Adjustment 자동 적용 | B 안정화 후 확장 권장 |

사용자의 자동 보정 방향은 확정이다. B/C의 상세 범위는 이번 제안이다. 기존 첨부의 ‘Mismatch만으로 자동 Adjustment 금지’와 양립하려면 원인·근거·사전 승인 정책을 확인해야 한다. 추후 C를 채택하면 자동 실행 주체/정책 승인과 관련 문서도 갱신한다.

### 분류별 처리

| 차이 | 권장 동작 |
|---|---|
| 지연/파일 일부 수신 | 완전성·마감 Window 확인 후 재조회. 아직 누락 확정하지 않음 |
| 중복 파일/이벤트 | hash/업무키 확인, 중복 효과 차단·관찰 기록 |
| 내부 금융 사실 존재·Projection 누락 | 원 사실의 같은 ID 재전달/멱등 재생. 기관 금융 호출 없음 |
| 원 Attempt와 일치하는 확정 기관 성공·내부 UNKNOWN | 인증된 근거 검증 후 소유 도메인 Recovery API로 결과 반영 |
| 입금 배분 누락 | 기관/은행 근거와 안정 키·잔액 상한으로 배분 복구 |
| 승인/취소/지급 금액·통화·MID·수취인 상충 | 자동 덮어쓰기 금지, 영향 거래/지급 보류·조사 |
| 은행 지급 결과 불명확 | 조회·대사, 새 송금 금지 |
| 정책 계산 오류/확정 정산 차이 | 원인·정책 근거 확인 후 별도 Adjustment. 원 확정 결과는 보존 |
| 외부 실패/거절인데 내부 성공 | 실패로 즉시 덮어쓰지 않고 원 성공·취소/사후 반환 근거를 조사 |

새 기관 요청은 복구 재생과 분리된 명령이다. 숫자가 작아도 승인·송금 재실행은 고위험일 수 있다. 금액이 같다고 identity 불일치를 자동 허용하지 않는다. fuzzy match는 조사 후보이며 자동 확정 근거가 아니다.

### 보정 실행 계약

대사 관찰 → Case 안정키/분류 → 증거·완전성·현재 버전 검증 → 위험판정/사전 승인 정책 → 자동 복구 또는 통제된 Adjustment → 재대사 → 해소 증거 기록.

- 보정 작업에 stable correctionKey, 원 거래/관찰/근거 참조, 정책 버전, 적용 범위·예상 금액·실행 상태를 둔다.
- observation/run 번호를 바꿔 같은 업무 보정을 반복하지 못하게 한다. 소유 도메인의 업무 effect key도 검사한다.
- 자동 수행자는 서비스 계정과 사전 승인 규칙을 사용한다. 운영자 승인 도용이나 direct SQL UPDATE를 사용하지 않는다.
- 금액 보정은 별도 금융 사실/Adjustment로 추가한다. 잘못된 보정의 복구도 역조정 이력으로 남긴다.
- 보정이 UNKNOWN/실패이면 현재 적용 여부부터 확인하고 같은 명령/ID로 재개한다. 무조건 새 보정을 만들지 않는다.
- 자동 실행의 건별/기간별/대상별 금액·건수·누적 예산, 조회/재시도 예산·회로차단·dry-run·중단 기능을 둔다.
- 사건에 따라 거래→MID→기관→전역으로 차단을 확대한다. 소유 플랫폼에 영속 차단을 명령하고 지급 직전에도 재검증한다. FINANCIAL의 Payment 위험 통보는 PAYMENT가 자기 권리/차단 상태로 적용하고 ACK한다.
- 해제는 지표 회복만으로 하지 않고 원인·대사 해소·현재 자금/권리 조건과 승인 규칙을 확인한다. 단순 후속 이벤트로 수동/고위험 보류가 사라지지 않게 한다.

## 5. 휴일 관리와 정산 세부

- 국내 최초 권장 업무 timezone은 Asia/Seoul. 사용자 날짜 규칙과 timezone 선택은 구별한다. UTC timestamp도 보존한다.
- MASTER가 버전 있는 Calendar/Override를 관리하고 FINANCIAL이 Snapshot으로 계산한다. 주말·공휴일·대체공휴일·특별영업/휴무·은행/기관별 캘린더를 지원한다.
- originalTransactionDate와 adjustedBaseDate를 별도 보존한다. 비영업일 거래는 nextBusinessDay로 이동한다.
- 정산주기 D+N의 N·D 포함 여부, 마감과 늦은 수신 정책은 미결이다. 권장: 보정된 기준일을 D로 하고 D+0은 당일, D+N은 이후 N 영업일을 센다. 예: 토요일 거래→다음 월요일이 영업일이면 기준일 월요일, D+2는 수요일. 중간 휴일이면 더 이동한다. 예시는 정산주기 확정이 아니다.
- 소급 휴일 변경은 기존 확정 정산을 덮어쓰지 않는다. 미확정 계산의 재산출과 확정 이후 일정 변경/Adjustment를 구별한다. 원 승인/취소일은 바꾸지 않는다.
- 캘린더 미래 기간이 없거나 버전이 상충하면 임의로 평일로 간주하지 않고 보류/알림한다.
- 후발 취소는 취소일의 새 Entry로 반영한다. 수수료 반환 정책은 원승인 근거이며 정산일은 취소 거래일이라는 두 규칙을 동시에 지킨다.

## 6. 전체 고려사항과 미결

1. 수수료/VAT: 구체 반올림·원 단위·포함/별도·세율·정률/정액·min/max·부분취소 누적 반환·마지막 잔액·환불/취소 별도 처리비.
2. 정산: 실제 주기/마감, 음수채무/이월과 회수 Scope, Statement/Payable 묶음키, 늦은 이벤트·기관 매입 거절.
3. 지급: 계좌 변경 효력과 진행 중 목적지 불변, 사후 은행 반환/부분 반환, 채무 Claim VOID 경합, 다중 MID 합산 지급.
4. 위험: 한도 승인·변경 권한, 승인 기준 선지급의 손실 책임/담보/보류금 정책, 기관 집중·대규모 취소·차지백.
5. 날짜: 승인일의 출처(기관 거래일/PG 시각), 자정 경계·늦은 승인·취소 파일, 캘린더 버전/기관 비영업일 차이.
6. 이벤트: PAYMENT 반환 예약/해제 및 승인/취소 사실의 전달·선행관계·누락 복구, 선지급 직전 Snapshot freshness. 직접 DB 접근으로 해결하지 않는다.
7. 출시: KRW/체크카드/일반 할부/고객 인증은 아직 추가 권장안 채택 전. 기존 승인된 국내 신용카드 범위를 자동 확대하지 않는다.
8. 실행: 실제 저장소·검증환경·기준선, API/schema/상태 전이, Simulator spec, 임의 운영 숫자 없이 버전 있는 fixture.
9. 운영: 자동 보정→과거 시점 복원→동일 Case 재생 때 이중 보정/기지급 재송신 방지. 감사/보존/정합성 완료 조건.
10. 법적/기관 통제: 자금 사용 가능 범위·회수/상계·보관/감독 의무는 실제 사업/계약 적용 검토와 연결한다. 기술 설정만으로 충족됐다고 보지 않는다.

## 7. 다음 선택 권고

선지급 B(여러 범위 한도), 관계 B(N:M Assignment와 명시 MID), 대사 B(근거 기반 자동 복구)로 시작하고 사전 승인 금액 보정 C를 확장한다. 운영 수치와 수수료·정산 값을 승인한 것과 개발 fixture를 지정한 것을 구분한다.
