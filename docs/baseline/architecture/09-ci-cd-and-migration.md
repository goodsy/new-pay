# 09. CI/CD / Migration

## 목적

독립 플랫폼의 배포와 스키마·이벤트 변경을 안전하게 이행하며 금융 효과를 보존한다.

## 범위

빌드·공급망·배포 관문, Flyway, 데이터 이동, 호환성 및 rollback/roll-forward를 다룬다.

## 핵심 규칙

- 검증한 Kotlin·Java·Spring·Gradle·MySQL 및 라이브러리 버전을 고정한다. 아티팩트는 한 번 빌드해 환경 간 승격하고 digest·SBOM·검사 결과를 보관한다.
- CI는 모듈 경계·단위·Repository·이벤트 계약·관련 장애 테스트·비밀 탐지·의존성 취약점 검사를 수행한다. 운영 전에는 기관 인증·보안·성능·복원 증거를 추가한다.
- DB별 독립 Flyway 이력·권한·migration job을 둔다. 애플리케이션 여러 replica가 동시에 운영 migration을 실행하지 않게 한다.
- 변경은 expand → 호환 배포 → 제한된 backfill → 검증 → 읽기 전환 → 관찰 → contract 순서로 수행한다.
- backfill은 소유 DB 안에서 멱등·중단/재개 가능하게 실행하고 부하를 제한한다. 도메인 의미가 바뀌면 Application Use Case 또는 검증된 변환 규칙을 사용한다.
- 구·신 앱, 구·신 이벤트 소비자가 공존할 수 있어야 한다. Outbox/DLQ의 과거 이벤트도 호환 검증에 포함한다.
- DB DDL은 자동 rollback된다고 가정하지 않는다. 파괴적 변경 후 구버전 앱이 기동 가능한지 별도로 판단한다. 코드 rollback, 스키마 복원, 금융 보정은 다른 절차다.
- 이미 발생한 승인·지급을 배포 rollback으로 되돌릴 수 없다. roll-forward와 대사·Adjustment를 우선 검토한다.
- Payment canary는 요청의 멱등성과 진행 중 Attempt를 유지한다. Worker canary는 소비 ownership·업무 키를 지켜 중복 실행을 통제한다.

## 예시 흐름

### 정책 필드 추가

```text
MASTER 새 정책 버전/호환 이벤트 추가
 → PAYMENT/FINANCIAL에 새 필드 수용 코드 배포
 → 스냅샷·backfill 검증
 → 새 정책 활성화 및 거래 버전 보존
 → 구버전·재생 기간 종료 확인
 → 불필요한 구 필드 제거
```

### 기존 통합 DB에서 분리

1. 소유권을 확정하고 다른 도메인 직접 Repository/SQL 접근을 제거한다.
2. 원본 소유 플랫폼의 로컬 Outbox와 대상 Inbox·업무 키를 먼저 도입한다.
3. 소유 플랫폼이 snapshot + 일관된 watermark를 내보내고 대상 DB에 적재한다.
4. 변경분을 따라잡고 거래 단위·건수·금액·정책 버전을 대사한다.
5. 제한된 쓰기 중지 또는 검증된 cutover 절차로 최종 경계를 맞춘다. 두 원본에 동시에 쓰지 않는다.
6. 연결을 신규 소유 DB로 전환하고 기존 접근 계정·네트워크 권한을 회수한다.
7. 지급·승인 외부 효과를 포함해 재검증한다. 신규 DB에 쓰기 시작한 뒤 단순 연결 rollback을 허용하지 않는다.

대상 시스템의 migration 완료만으로 cutover를 승인하지 않는다. snapshot 중 변경·누락, 이벤트 겹침, 기존 지급의 중복 실행을 검증해야 한다.

## 금지사항

- 모든 DB를 한 migration 트랜잭션으로 갱신하는 것.
- 운영 중 정책·금액 컬럼을 호환 단계 없이 삭제·의미 변경하는 것.
- 동일 금융 업무를 구·신 시스템에서 동시에 원본으로 처리하는 것.
- rollback 시험 없이 “이전 이미지 재배포”만을 복구 계획으로 쓰는 것.

## 구현 체크리스트

- [ ] 플랫폼별 배포·migration·소비자 호환 행렬이 있다.
- [ ] Flyway 이력·checksum·lock·DDL 부하를 검증했다.
- [ ] backfill 및 cutover의 중단/재개·대사·승인 조건이 있다.
- [ ] 코드 rollback과 데이터/금융 복구 절차를 구분했다.
- [ ] 운영 배포 근거·담당자·변경 이력·관찰 지표를 기록한다.
