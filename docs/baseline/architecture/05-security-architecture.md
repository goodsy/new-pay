# 05. Security Architecture

## 목적

가맹점·운영자·내부 서비스·외부기관 사이 신뢰 경계를 보호하고 금전·민감정보 조작을 통제한다.

## 범위

인증·인가, Credential, 네트워크, 데이터 보호, 감사, 결제 화면과 운영 도구를 다룬다. 세부 법적 적용 범위는 운영 전 별도 확인한다.

## 핵심 규칙

- 외부 API는 Credential을 MID·환경·허용 작업에 연결한다. 인증 후 모든 거래 ID 조회·변경에서 소유 MID를 검증한다.
- 서버용 비밀 키는 결제창·브라우저로 전달하지 않는다. 브라우저 토큰은 범위·금액·주문·만료시간을 제한하고 서버에서 금액을 검증한다.
- TEST/LIVE 데이터·Credential·기관 endpoint를 분리한다. Sandbox 요청이 운영기관으로 나가지 않도록 설정과 네트워크로 방어한다.
- 내부 운영자는 SSO/MFA, 최소 권한과 역할별 인가를 적용한다. 지급·계좌 변경·정산 조정·재처리 권한을 조회 권한과 구분한다.
- 중요 금액·정책·계좌 변경은 요청자와 승인자를 분리하고 변경 전후 값·사유·범위·증빙을 남긴다. 계좌 변경과 이미 생성된 지급의 적용 시점을 명시한다.
- 서비스 간 통신은 서비스 신원·인가·전송 암호화를 적용한다. DB는 사설망에 두며 소유 서비스 계정에만 접근을 허용한다.
- 비밀정보는 Secret Manager 등 관리 저장소에 보관하고 회전·폐기·만료 알림을 제공한다. 비밀을 로그·이벤트·이미지·소스에 포함하지 않는다.
- 검증 전용 API 키는 적절한 단방향 검증값으로 저장한다. 기관 호출에 원문이 필요한 비밀은 관리 키로 암호화하고 접근을 통제한다.
- 카드 정보는 기관 토큰·호스티드 입력 등 최소 수집 구조를 우선한다. 민감 인증정보를 승인 후 저장하지 않는 기준을 적용한다. 카드 데이터 취급 범위와 PCI DSS 등 적용 요건은 운영 전 별도 평가한다.
- 개인정보·계좌는 필드 단위 접근·마스킹·암호화·목적별 보존·파기를 적용한다. 백업과 감사 저장소도 같은 통제 대상이다.
- 로그의 paymentId·mid 등을 근거 없이 공개하지 않는다. 검색·다운로드·원문 접근은 별도 감사한다.
- 결제창은 XSS·CSRF·프레임 삽입·redirect 조작을 방어한다. return URL은 허용 목록으로 제한한다. Webhook URL은 SSRF·사설망·redirect 우회를 방어하고 서명·재전송 방지를 제공한다.

## 예시 흐름

```text
운영자 A: 지급 계좌 변경 요청 + 사유
 → 소유권·권한 검증 / 기존 값과 변경값 기록
 → 운영자 B 승인
 → MASTER 변경 + Outbox 커밋
 → FINANCIAL 해당 버전 수신 / 지급 정책에 따라 적용
 → 지급 실행 시 승인된 계좌 버전과 근거 보존
```

## 금지사항

- 다른 MID의 거래를 ID만으로 조회하거나 취소하는 것.
- 프런트엔드에서 보낸 금액·역할을 신뢰하는 것.
- 운영자 공유 계정·공유 DB root 계정 사용.
- 감사 이벤트를 일반 로그처럼 변경·삭제할 수 있게 하는 것.
- API 키 폐기가 승인 경로에 전달되지 않는 무기한 로컬 캐시.

## 구현 체크리스트

- [ ] 신뢰 경계·위협 모델·민감 데이터 목록을 작성했다.
- [ ] MID 격리와 역할별 권한을 부정 테스트로 검증했다.
- [ ] 비밀 회전·폐기와 긴급 차단의 최대 전파 지연을 시험했다.
- [ ] 로그·이벤트·백업의 민감정보 노출을 검사했다.
- [ ] 중요 변경의 이중 승인·감사·보존 정책을 적용했다.
