# PayCore 과도한 설계와 관리 비용 진단 (COMPLEXITY-ASSESSMENT)

- 작성일 2026-11-20. 기준 커밋은 `378aff7`이다. 분석 단계라 소스·하네스·문서는 바꾸지 않았다.
- 표기: **[사실]**은 파일·명령·git 집계로 확인한 것, **[추정]**은 해석이나 제안이다.
- 근거 상세는 CURRENT-STATE.md, DOMAIN-ASSESSMENT.md, FRONTEND-ASSESSMENT.md에 있다.

## 1. 결론

**변경 비용의 주 원인은 금융 도메인이 아니다. 주변의 검증·기록·구조 관행이 비용을 만든다.** 비용 원천을 큰 순서대로 적으면 다음과 같다. [사실 + 추정]

1. **매 배치마다 도는 약 55분짜리 전체 게이트.** 프런트만 바꿔도 Kotlin 시험 5,096개를 전부 다시 돈다.
2. **같은 사실을 4곳에 기록하는 관행.** 명세 본문·명세 rev 기록, tasks.json, 커밋 메시지, DECISIONS가 그 4곳이다. 문서 34,796줄, tasks.json 1.1MB, DECISIONS.md 109KB가 쌓였다.
3. **구조 단언 시험.** 화면 모양만 바꿔도 시험 순증이 main 순증의 3.6배가 된다.
4. **구현 1개뿐인 Port와 Domain↔JPA 이중 모델.** persistence 코드가 domain 코드보다 크다.
5. **같은 모듈 안 복제.** 관리자 승인 서비스 4개, 시계 Port 11개, 화면 잠금 로직 3곳이 여기에 해당한다.

**가치가 확인된 장치는 따로 있다.** 독립 리뷰, 변이 시험, DB 권한(append-only), 아키텍처·쓰기 경로 가드, argv 고정·fingerprint가 실제 결함을 잡았다. 이 장치들은 유지 대상이다. [사실]

### 2.2 게이트가 실제로 잡은 것 [사실, tasks.json 기록 기준]

FAIL 30건의 원인은 다음과 같다.

| 원인 | 건수 |
|---|---|
| timeout·자원 부족 | 9건 이상 |
| 불안정 시험(fixture·환경) | 약 10건 |
| 아키텍처·목록 가드가 잡은 누락 | 3~4건 |
| **업무 로직 결함** | **기록상 확인 안 됨** |

업무 결함은 배치 안의 RED/GREEN 단계와 **독립 리뷰·변이 시험**이 먼저 잡았다. 아래는 실제 사례다.

- 웹훅 INSERT 전면 실패(CHECK 3819)
- 승인 뒤 감사 누락으로 승인이 정체
- TX1 rollback 때 TOTP 소비가 함께 되돌아감
- append-only 표의 UPDATE/DELETE가 DB 권한으로 막혀 있지 않음
- 화면에 내부 키 노출

[추정] 전체 게이트가 고유하게 기여하는 부분은 **모듈 사이 회귀 확인과 불안정 시험 노출**이다. 그렇다면 배치마다 돌릴 필요는 없고, 기능 종료 시 한 번이면 같은 가치를 얻는다.

### 3.2 문제 유형 [사실]

**같은 결정의 4중 기록.** MNS 사례에서 "앞부분 LIKE + ESCAPE, 대소문자 구분, 코드와 함께면 400, 감사 없음"이 아래 네 곳에 거의 같은 문장으로 있다. 검증 수치는 세 곳에 반복된다.

- tasks.json decisions
- 커밋 메시지
- 명세 본문
- 명세 rev 기록과 tasks.json reviewFix

**최신 규칙을 찾기 어렵다.**

- 명세 머리말이 rev 0.1부터의 개정 기록으로 시작한다. 예: MERCHANT-OPS-002 rev 0.9.4는 정정 30회, MERCHANT-CODE-001 rev 0.4.12는 정정 31회다.
- 본문 규칙, 개정 이력, 구현 기록, 리뷰 지적이 한 파일에 섞여 있다.
- DECISIONS는 행 단위 대체 방식이라 독자가 연결을 직접 따라가야 한다. 대체 표식이 24회 나온다.

**같은 규칙의 다중 서술과 낡은 서술.**

- 주문 key 용어가 문서마다 다르다. MID와 merchantAccountId가 섞여 쓰인다.
- 2인 승인 대상 전체를 보려면 DECISIONS 여러 행을 이어 읽어야 한다.
- 수수료 Snapshot은 7곳 이상에서 서술된다.
- 낡은 서술 예: HARNESS-GUIDE:56의 "commands.json은 빈 목록"(실제로는 13개), D-ENV-001 "Boot 3.x", settings.gradle.kts의 "ADMIN DB 없음", README가 starter 팩 설명 그대로인 점, workspace.css의 다크 모드 주석.

**기록 스키마가 비정형이다.**

- 같은 의미에 키 이름이 여러 개다: `review`/`reviewRounds`/`specReview`/`reviewFix1`, `decisions`/`coordinatorDecisions`.
- 배치별 임시 키(`biz1`~`biz4`, `mc3a` 등)가 약 260KB다.
- `nextResumeAction`은 70개 task 중 24개에만 있다.
- progress.json은 약 11-14 상태에 멈춰 있다.

**증거가 저장소 밖에 있다.** `~/gate-logs/...`를 참조하므로 다른 clone에서는 확인할 수 없다.

## 4. 코드 구조 비용 [사실 → DOMAIN·FRONTEND 문서 상세]

| 항목 | 규모 | 판정 [추정] |

## 5. 과하지 않은 것 (유지해야 할 장치) [사실 근거]

| 장치 | 유지 이유 |
|---|---|
| 서비스·DB 분리와 DB별 계정·표 단위 권한 | cross-DB 0건, append-only를 실행 계정 수준에서 강제한다. 리뷰가 실제 결함을 잡고 강화했다 |
| 순수 Domain과 ArchUnit 규칙 | 금융 규칙의 위치와 호출 경로를 강제한다(예: `ReturnBalance.reserve`는 CancelStart에서만) |
| 독립 Reviewer + 변이 시험 | 실제 결함을 주로 잡은 장치다 |
| golden 계약 시험 | 서비스 사이의 의도된 복제가 계속 일치하는지 보장한다 |
| argv 고정 실행기, fingerprint 전후 비교, 시험 하한, skip = FAIL | 비용이 낮고 검증 신뢰를 지탱한다 |
| 결과 불명 재전송 잠금, 내부 키 DOM 검사, CSP 시험 | 금융·보안 경계다 |

## 7. 사실 vs 추정

- **사실**: 게이트 순서·시간·판정 수, timeout 변천, fingerprint 범위, 기록·문서 규모, 4중 기록 사례, 낡은 서술 위치, 커밋 구성 비율, MNS 비용, FAIL 원인 분류(기록 문구 기준), 코드 구조 수치.
- **추정**:
  - "게이트가 업무 결함을 잡은 기록 없음"이 실제 기여 전부라는 해석. 세션에서 기록되지 않은 사례는 알 수 없다.
  - 단순화 효과 수치.
  - 유지·축소 판단.
