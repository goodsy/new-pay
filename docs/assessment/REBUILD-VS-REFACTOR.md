# PayCore 재개발 대비 개선 비용 비교 (REBUILD-VS-REFACTOR)

- 작성일은 2026-11-20, 기준 커밋은 `378aff7`이다. 분석 단계라 소스를 바꾸지 않았다.
- 표기는 두 가지다. **[사실]**은 진단 문서 3종(CURRENT-STATE·DOMAIN·FRONTEND)과 COMPLEXITY에서 확인한 수치다. **[추정]**은 작업량·위험 산정으로, 아래 §1의 가정에 의존한다.
- **결론: A안(전체 유지·리팩터링)을 기본으로 하고, B안 요소 중 효과가 확인된 것만 골라 넣는 방식을 권장한다. C안(전면 재개발)은 권장하지 않는다.**

### 1.2 처리 속도 기준 [사실 → 산정 근거]

- 최근 7일 동안 커밋 44개를 만들었다. 커밋당 평균 1,668줄이 바뀌었다.
- 작은 기능 MERCHANT-NAME-SEARCH-001(1,122줄, 코드 114줄)은 리뷰 3회와 게이트 3회(2.7시간)를 거쳐 약 0.5~1일이 걸렸다.
- 화면 레이아웃 6개 배치는 약 1.5일, 게이트 6회(약 5.5시간)가 걸렸다.
- 이 산정에서 "작업일"은 **지금 방식(에이전트 구현 + 독립 리뷰 + 전체 게이트)으로 처리하는 하루**를 뜻한다. 사람이 혼자 일하는 날 수가 아니다.

### 1.3 가정 [추정]

- 신규 코드의 처리 속도는 위 기준과 같다고 본다. 프로세스를 단순화하면 A·B·C 모두 30~50% 빨라진다고 본다(COMPLEXITY §6).
- 재개발(C)에서도 금융 규칙은 기존 코드·문서·결정을 명세로 쓴다. 그래도 **동시성·rollback·멱등성은 다시 증명해야 한다.**
- 미구현 영역(정산·지급·대사·생명주기)은 세 안 모두에서 똑같이 남는 일이다. 그래서 비교에서는 뺐지만, **C안은 이 일의 시작을 그만큼 늦춘다.**

## 2. 세 방안 정의

| 방안 | 내용 |
|---|---|
| **A. 현재 프로젝트 전체 유지·리팩터링** | 구조는 그대로 둔다(5서비스·5DB·헥사고날·Domain↔JPA 분리). 프로세스를 단순화하고, 같은 모듈 안의 중복 제거·화면 통합·문서 정본화 같은 국소 개선만 한다 |
| **B. 핵심 도메인과 시험을 보존한 선별 재구성** | Domain·golden·동시성 시험·DB 스키마·권한은 보존한다. application/adapter 층(단일 구현 Port 정리, Domain↔JPA 이중 모델 축소)과 관리자 화면(스타일 단일화, 큰 화면 재작성), 문서 체계를 다시 짠다 |
| **C. 신규 프로젝트로 전면 재개발** | 새 저장소에서 처음부터 만든다. 기존 코드·문서는 참고 명세로만 쓴다 |

## 3. 비교표 [추정 — §1 가정 기준]

| 항목 | A. 유지·리팩터링 | B. 선별 재구성 | C. 전면 재개발 |
|---|---|---|---|
| 예상 작업량(현재 방식) | **8~15 작업일**(프로세스 3~5 + 코드·화면·문서 5~10) | **30~50 작업일** | **90~150 작업일** + 미구현 영역은 별도 |
| 프로세스 단순화 후 | 6~10 작업일 | 20~35 작업일 | 60~100 작업일 |
| 변경 파일 수 | 약 150~300(코드), 문서·기록 재편 별도 | 약 800~1,300(persistence 21.5K줄·adapter·화면 대부분) | 전부(약 2,700+ 새로 작성) |
| 보존되는 것 | 코드·시험·스키마·결정 전부 | Domain·golden·동시성 시험·스키마·권한·결정 | 결정과 문서(명세 역할)만. 코드·시험은 새로 작성 |
| 재검증 범위 | 바꾼 모듈의 기존 시험 + 기능 종료 시 전체 게이트 | 거의 모든 adapter·통합 시험을 다시 작성하거나 다시 증명. golden·동시성은 재통과 확인 | 전부. 동시성·rollback·멱등·Recovery·매입 3축·2인 승인을 처음부터 다시 증명 |
| 기능 정지 기간 | 거의 없음(작은 단위로 섞어 진행) | 2~4주, 신규 기능 중단 | 3~6개월, 신규 기능(정산 등) 중단 |
| 주요 위험 | 낮음. 국소 변경이 회귀하면 기존 시험이 잡는다 | **중간.** TX 경계·잠금 순서·저장 순서(FK)·reconstitute 검사를 옮기다 회귀할 수 있다. Domain↔JPA 축소는 사용자 원칙 변경이 필요하다 | **높음.** 시험으로 증명된 경쟁·불명·회복 동작을 잃을 수 있다. 결정 253건이 코드에 담긴 미묘한 해석(errata·리뷰 수정 다수)을 놓칠 수 있다. 일정이 크게 늘어날 수 있다 |
| 얻는 것 | 변경 비용이 가장 크게 내려간다(게이트·기록·구조 단언이 주 원인이기 때문). 위험이 가장 작다 | persistence·Port 계층이 얇아져 기능당 파일 수가 줄어든다. 화면 모양이 하나로 정리된다 | 처음부터 단순한 구조가 될 *가능성*. 단, 같은 원칙(DDD/헥사고날·JPA 분리·서비스 분리)을 지키면 결과 구조는 지금과 비슷해진다 |
| 미구현 영역 착수 | 즉시 가능 | 재구성 후 | 재개발 후(수개월 지연) |

## 4. 판단 근거

1. **비용의 주 원인은 코드 구조가 아니라 프로세스다.** [사실 + 추정]
   - 원인은 세 가지다: 55분짜리 전체 게이트가 배치마다 도는 것, 같은 내용을 네 곳에 기록하는 것, 구조 단언 시험(COMPLEXITY §1).
   - 이 셋은 코드를 버리지 않고도 바로잡을 수 있다. 재개발해도 같은 프로세스를 쓰면 같은 비용이 다시 생긴다.
2. **가장 값진 자산은 시험으로 증명된 금융 동작이다.** [사실]
   - 주문 슬롯·UNKNOWN 유지·취소 잔액·Hold·append-only·2인 승인 같은 동작이 동시성 88건, golden 29+, FaultInjection 시험으로 증명돼 있다.
   - C안은 이 증명을 다시 해야 한다. B안은 adapter를 바꾸면서 일부를 다시 증명해야 한다.
3. **서비스·DB 분리는 과하지 않다.** [사실]
   - cross-DB 접근이 0건이고, 계정 단위 권한으로 append-only를 강제한다. 설계상 9개였던 실행 단위도 이미 5개로 합쳐져 있다.
   - 더 합치려면 baseline 01과 TECHNOLOGY §5를 바꾸는 정책 결정이 필요하다. 얻는 이득(게이트 시간·기동 단순화)도 측정되지 않았다.
4. **Domain↔JPA 이중 모델은 실제 비용이지만 사용자가 지정한 원칙이다.** [사실]
   - B안의 핵심 절감이 여기서 나오므로 B안을 하려면 먼저 사용자 결정이 필요하다.
   - 결정 없이 가능한 B 요소는 화면 통합과 큰 화면 분할 정도다.
5. **정산·지급·대사가 아직 없다.** [사실]
   - PG의 돈 흐름 후반부다. 재개발은 이 일을 수개월 늦춘다. [추정]

## 5. 권장안: "A + 선별된 B 요소"

| 단계 | 포함 | 출처 |
|---|---|---|
| 1 | 프로세스 단순화: 게이트 범위, 기록 스키마, 명세 정본화, 커밋 메시지 | A |
| 2 | 금융 안전 정비: 화면 결과 불명 잠금 통합과 규칙 정렬, 낡은 서술 정합화 | A |
| 3 | 같은 모듈 안 중복 제거: 승인 서비스 helper, Clock, 입력 규칙, Simulator 규칙 보강 | A |
| 4 | 화면 통합: 스타일 단일화, 줄 컴포넌트 통합, 구조 단언을 동작 단언으로 전환 | A |
| 5 | 큰 화면 분할(가맹점 조회·등록·매입·개통) | B 요소(결정 불필요) |
| 6 (선택, 사용자 결정 후) | Domain↔JPA 이중 모델 축소, 단일 구현 Port 정리 | B 요소(원칙 변경) |

권장안 예상 작업량은 단계 1~5 기준 **10~18 작업일**이다. 프로세스가 단순해진 뒤에는 이 중 상당 부분이 더 빨라진다. 단계 6을 하면 15~25 작업일이 더 든다. [추정]

순서와 완료 기준은 RECOVERY-ROADMAP.md에 있다.

## 7. 사실 vs 추정

- **사실**: §1.1~1.2의 수치, 비용 원인의 존재, 보존 자산·미구현 영역, 서비스 분리가 실제로 하는 일, 원칙(JPA 분리)이 사용자 지정이라는 점.
- **추정**: 작업일·변경 파일 수·기능 정지 기간·위험 등급, 프로세스 단순화 효과(30~50%), 재개발 뒤 구조가 비슷해질 것이라는 판단. 실제 값은 단계 1 이후 처리 속도를 측정해서 보정한다.
