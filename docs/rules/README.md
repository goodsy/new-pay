# 업무 규칙 대장

현재 유효한 업무 규칙의 정본. 설계: `docs/repository/RULE-GOV-001-BUSINESS-RULE-GOVERNANCE.md`. 결정 이력은 `docs/DECISIONS.md`, 질문 원문은 `harness/questions.json`.

## 도메인 파일

| 파일 | 도메인 |
|---|---|
| `BIZ.md` | 사업자·가맹점 기준정보(MID·Site·계약·권리·사업자 계약 접수) |
| `PAY.md` | 결제 생성·결제시도·승인·결제창 |
| `CAN.md` | 취소·환불·거래 운영 |
| `FIN.md` | 매입·정산·지급·대사 |
| `WH.md` | 웹훅·외부 통지 |
| `ADM.md` | 관리자 인증·권한·감사·개인정보 |

## 형식

각 파일은 절(업무 주제)별 표 하나 이상. 열 순서 고정:

`| ID | 규칙 | 상태 | 출처 | 근거 | 적용 명세 | 검증 |`

- **ID** `BR-<도메인>-<3자리>`, 재사용 금지.
- **규칙** 한 문장, 검증 가능한 형태. 화면 배치·구현 방식은 넣지 않는다.
- **상태** `확정` · `제안` · `대체됨→BR-…` · `Demo값` · `미결(Q-…)`.
- **출처** `사용자` · `적용`(Coordinator가 사용자 답에서 끌어냄, 사용자 확인 전 = 상태 `제안`) · `기준`(baseline 확정 문서).
- **근거** D-ID·Q-ID·문서 §(쉼표 구분).
- **적용 명세** `docs/repository/…md §`.
- **검증** 시험 `파일명::시험 이름 요약` 또는 `없음`.

파일 끝 `## 진단` 절: 대체 사슬, 결정 간 충돌, 정책서·명세 본문 불일치, 시험 없는 확정 규칙, 코드와 다른 규칙, 미결 질문 후보.

## 용어 절 (`## 0. 용어`)

도메인 대장 맨 앞에 둘 수 있다. 용어 정의의 정본이며 다른 문서는 참조만 한다(D-GOV-006 ②·D-GOV-007 ②·D-GOV-008).

- 형식: `- **용어**: 정의(1~2문장, 구현 세부 없음). _Avoid_: 피할 말. — 근거 ID`
- **규칙은 넣지 않는다.** "~할 때만", "~는 거절" 같은 업무 규칙은 BR 행으로 쓰고 용어 절은 BR-ID를 가리킨다.
- 작성 절차(새 기능 명세를 시작할 때, 설치 없이 적용 — D-GOV-009·Matt Pocock domain-modeling 참고):
  1. 같은 개념을 문서·화면·코드에서 모아 한 표로 대조한다(근거 file:line·문서 §).
  2. 경계 시나리오로 용어의 경계를 시험하고 현재 코드 동작을 확인한다.
  3. 사실은 에이전트가 찾고 결정만 사용자에게 묻는다. 묻기 전에 확정 결정(D-*)과 대장 `확정` 행을 뺀다.
  4. 질문은 한 번에 3개 이하(HARNESS-GUIDE §4), 대안은 `harness/questions.json` 안에 문장으로 적는다.
  5. 대장 반영 전 독립 리뷰를 거치고, 정식 용어 선택·반영은 사용자 확인 후에 한다.
- 만들지 않는 것: `GLOSSARY.md`, `docs/adr/`, `docs/agents/`, CLAUDE.md의 별도 Skill 블록.
