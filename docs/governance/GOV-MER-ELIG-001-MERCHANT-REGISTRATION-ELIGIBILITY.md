- 범위: BR-BIZ-279·280(새 가맹점 등록 관문)과 사용자 정의(D-GOV-011 ①, Q-RC-4 답). 사업자 계약 접수(MERCHANT-FLOW-001)와 가맹점 계약(Contract·Revision·CSA, MASTER-DOMAIN-001)이 이 관문과 어떻게 이어지는지를 본다.

## 0. 한눈에 — 핵심 결론

1. **[사실] PayCore에는 '계약'이 두 개 있고, 둘 다 사용자가 말한 '등록하려는 가맹점·서비스 범위에 해당하는 유효한 계약'에 그대로 맞지 않는다.**
   - (a) **계약 접수 건**(`ContractIntake`, 사업자 단위): 가맹점보다 먼저 존재할 수 있다. 하지만 '계약 완료'는 계약서를 받았다는 영업 기록일 뿐이다(BIZ.md 용어 절 :35, BR-BIZ-270). 서비스 범위·효력 기간·정지 상태가 없다.
   - (b) **가맹점 계약**(`Contract`·Revision·CSA): 결제를 허용하는 근거이고 범위(Scope)·효력 기간·서비스 종류가 있다. 하지만 **대상 가맹점이 먼저 있어야 만들 수 있다**(DB FK `V1__master_core.sql:95`, `ContractScope.requireValid` `M/domain/ContractScope.kt:29-43`). 그래서 아직 없는 '새 가맹점'의 등록 자격 근거가 될 수 없다.
2. **[해석] 현재 불변식에서는 '최신 접수 건 = 계약 완료'(BR-BIZ-280)와 '해지되지 않은 계약 완료 건이 있음'의 판정 결과가 같다.** 계약 완료 건이 있으면 새 접수를 거절하기 때문이다(BR-BIZ-277, `M/domain/ContractIntake.kt:61-62`, DB `uk_cin_active` `V19__contract_intake.sql:34-37`). RULE-CONFIRM Q4가 차이로 든 경우('해지 뒤 새 접수 진행 중')는 두 기준 모두에서 등록이 막힌다.
3. **[해석] 사용자 정책의 "기존 유효 계약이 있으면 신규 접수·변경 심사·반려만으로 막지 않는다"는 현재 모델에서는 일어날 수 없는 상황을 전제한다.** 유효 계약(계약 완료)이 있는 동안 새 접수·변경 심사를 만들 수 없기 때문이다(D-FLOW-004 ①). 이 문장을 실제 동작으로 만들려면 D-FLOW-004 ①("해지 뒤에만 새 접수")을 바꾸거나, '변경 접수'를 따로 정의해야 한다.
4. **[사실] 사용자가 든 차단 사유 중 접수 건에는 '해지'만 있다.** 접수 건에는 효력 기간이 없어 '만료'가 없고, 정지 상태도 없다(`M/domain/ContractIntakeStatus.kt:12-18`). 가맹점 계약에는 '만료'(효력 기간 종료)는 있지만 '철회·정지'는 아직 구현되지 않았다(MASTER-LIFECYCLE-001 BACKLOG, `M/domain/Contract.kt:14`).
5. **[사실] '서비스 범위'는 가맹점 등록 시점에 알 수 없다.** 가맹점 등록 명령에는 서비스 입력이 없다(`RegisterMerchantCommand` — `M/application/provided/MerchantOnboardingUseCase.kt:95`). 서비스 종류는 그 뒤 CSA를 추가할 때 정해진다(`:165`). 접수 건의 희망 서비스(`CARD_AUTH`·`CARD_KEYIN`, 효력 없음)와 CSA 서비스 종류(`CARD_PG_PAYMENT`)도 분류가 다르다.

→ 사용자 정의를 그대로 구현하려면 **'유효 상태'를 가진 사업자 단위 계약**이라는 새 개념이 필요하다. 그 정체·범위·해지 효과는 사용자 결정 대상이다(§7 Q-ELIG-1~3).

## 4. 추가 검토 5항목

### 4.1 사업자별 복수 계약 허용 여부

- **정해진 것**
  - 접수 건: 사업자당 열린 건 ≤ 1, 계약 완료 건이 있으면 새 접수 거절(D-FLOW-003 ①, D-FLOW-004 ①, BR-BIZ-277). 그래서 '계약 완료(유효)' 접수 건은 사업자당 최대 1개다(`V19:34-37`). 과거 건(불가·해지)은 여러 개가 남는다(1:N 이력).
  - 가맹점 계약: 한 사업자는 가맹점마다 계약을 가진다(BR-BIZ-001·102·103). 한 가맹점 같은 서비스 종류의 기간 겹치는 유효 계약은 금지다(D-GOV-003 ①, 미시행 GM-03).
- **미정**
  - 사업자 단위 '유효 계약'을 서비스 종류별로 여러 개 둘지, 하나에 범위를 여러 개 담을지.
  - 변경 접수가 진행 중일 때 '유효 계약 1 + 진행 중 접수 1'의 공존을 허용할지(U-3 전제). → **Q-ELIG-2**

### 4.2 계약–가맹점 연결 관계

- **정해진 것**
  - 가맹점 계약은 대상 가맹점 하나다(D-MD-010·013). 다른 가맹점의 계약은 새 가맹점의 근거가 될 수 없다. 같은 사업자라도 마찬가지다(BR-BIZ-103). **[해석]** 그래서 "같은 사업자의 기존 가맹점 계약이 유효하면 새 가맹점 등록 가능"으로 읽는 해석은 현행 모델과 맞지 않는다.
  - 가맹점 계약은 대상 가맹점 행이 있어야 생긴다(FK `V1:95`).
- **미정**
  - 사업자 계약(또는 접수 건)과 가맹점 사이의 연결 기록이 없다. 등록 때 근거 계약을 가맹점에 남길지, 남긴다면 불변인지가 정해지지 않았다.
  - 사업자 계약 범위와 가맹점 CSA 서비스 종류 사이의 포함 관계를 검사할지, 검사한다면 어디서 할지(등록 때 / CSA 추가 때)도 미정이다. 현행 원칙은 "기존 가맹점의 후속 명령은 접수 건을 보지 않는다"(BR-BIZ-279 괄호, D-BIZ-001)이다. → **Q-ELIG-2**

### 4.3 계약 변경·갱신 정책

- **정해진 것**
  - 접수 건의 종결은 비가역이다. 다시 진행하려면 새 접수 건을 만든다(D-FLOW-001 ②, BR-BIZ-272). 계약 완료 상태에서 '변경 접수'를 할 경로는 없다(해지 → 새 접수만).
  - 가맹점 계약: Scope·기간 변경은 새 Revision(D-MD-004), 적용 Revision은 번호 최대(D-MD-011), 같은 CSA 갱신은 MID 유지(D-MD-004, 명령 미구현), 소급 시작 금지(BR-BIZ-107).
- **미정**
  - 사업자 단위 계약의 변경·갱신(범위 추가, 기간 연장) 방식.
  - 변경 심사 중이거나 반려됐을 때 기존 유효 상태를 유지하는 방식(U-3). → **Q-ELIG-2**

## 6. 대체 문장 초안과 영향 범위

### 6.1 BR-BIZ-279·280 대체 문장 초안 (§7 권장안이 채택될 때 — 결정 아님)

- **BR-BIZ-279(대체 초안)**: 새 가맹점 등록은 사업자 생명주기가 ACTIVE이고 등록 상태가 REGISTERED이며, **판정 시각에 그 사업자의 유효한 사업자 계약**(해지·정지가 아니고 효력 기간 안이며 서비스 범위가 하나 이상)이 있을 때만 허용한다. 계약 접수 건의 진행 상태(상담 중·계약서 접수·계약 불가)는 판정 입력이 아니다. 기존 가맹점의 후속 명령은 사업자 계약을 보지 않는다.
- **BR-BIZ-280(대체 초안)**: 유효 판정은 사업자 행 잠금 뒤 같은 MASTER 로컬 TX에서 그 사업자의 사업자 계약 현재 상태로 한다(판정 시각 = 잠금 뒤 시각). 변경·갱신 접수가 진행 중이거나 반려되어도 기존 유효 계약은 그대로 유효하다. '최신 접수 건' 기준은 쓰지 않는다(D-GOV-011 ①).
- **대안 초안(Q-ELIG-1이 '현행 접수 건 유지'일 때)**: "새 가맹점 등록은 사업자 ACTIVE·REGISTERED이고 그 사업자에 **해지되지 않은 계약 완료 접수 건**(이관 포함)이 있을 때만 허용한다." 현재 불변식(BR-BIZ-277)에서는 '최신' 기준과 결과가 같다. 대신 나중에 새 접수를 유효 계약과 공존시켜도 U-3을 지킨다. 이 경우 만료·정지·범위(§5.2 10~13)는 다루지 못한다.

## 7. 사용자 결정 필요 질문 (3개)

### Q-ELIG-1 (금융·상태 의미) '유효한 계약'은 무엇인가

- **권장: (a) 사업자 계약을 새로 두고 접수 건과 분리한다.** 접수 건(진행 축: 상담 중·계약서 접수·계약 불가)은 지금처럼 영업 기록이다. '계약 완료' 전이 때 **사업자 계약**(유효 축: 유효·정지·해지·만료)을 만들거나 갱신한다. 새 가맹점 관문은 사업자 계약의 유효 상태만 본다. 결제 허용 근거는 지금처럼 가맹점 계약 Revision 승인(2인)뿐이다(D-MD-004·012·015, BR-BIZ-270 유지). MERCHANT-FLOW-001 선택지 C(§4.3)의 '사업자 기본 계약'과 비슷하지만 2인 승인과 가맹점 Revision 승인 조건은 더하지 않는다.
- 대안:
  - (b) 접수 건 하나에 유효 상태 열을 더한다. 변경 심사는 같은 건 안의 하위 상태로 둔다. 변경 범위는 가장 작지만 진행과 유효가 한 Aggregate에 섞인다.
  - (c) 가맹점 계약을 관문 근거로 쓰도록 순서를 바꾼다(계약 → 가맹점). D-MD-004·010·013과 정면 충돌하고 MID·Snapshot을 다시 설계해야 한다(MERCHANT-FLOW-001 선택지 B). **비권장**.
  - (d) 현행 접수 건 유지 + §6.1 대안 초안('해지되지 않은 계약 완료 건'). 만료·정지·범위(§5.2 10~13)는 다루지 못한다.
- 영향: (a)·(b)는 MASTER 표 추가·변경(V19 후속 migration), FLOW-1 이관 건 재이관, BR-BIZ-270~282 개정이 필요하다. 결제·정산 무영향은 유지된다(Q-ELIG-3 권장안일 때).
- 막히는 작업: **FLOW-3**(관문), FLOW-2(전이 명령 — 계약 완료 전이가 사업자 계약을 만드는지), 이관 규칙.

### Q-ELIG-2 (상태·키 동일성) 사업자 계약의 범위·복수·연결·변경 — Q-ELIG-1이 (a)·(b)일 때

- **권장(묶음)**:
  - ① 범위 = **서비스 종류 집합**(지금은 `CARD_PG_PAYMENT` 하나 — D-AUTH-001 범위). 가맹점 범위는 두지 않는다(그 사업자의 모든 새 가맹점). 희망 서비스(체크, 효력 없음)와는 다른 값이다.
  - ② 사업자당 **동시에 유효한 사업자 계약 1개**(범위 여러 개 가능, D-GOV-003 ① 겹침 금지 준용).
  - ③ 변경·갱신 = 같은 사업자 계약의 **새 판**(범위 추가·기간 연장). 변경 접수가 진행 중이거나 반려돼도 기존 판은 유효하다(U-3). 이를 위해 BR-BIZ-277/D-FLOW-004 ①을 '유효 계약이 있으면 **변경 접수**만 허용'으로 바꾼다.
  - ④ 효력 기간 = 시작일 필수, 종료일 선택(KST 날짜, 소급 금지 — BR-BIZ-107 준용). 종료일이 지나면 '만료'.
  - ⑤ 정지·해제·해지 = OPERATOR 1인 + 사유(효과가 새 가맹점 관문뿐이라 D-FLOW-001 ②의 1인 원칙과 같다).
  - ⑥ 가맹점 등록 때 근거 사업자 계약과 판 번호를 가맹점 등록 이력에 **불변으로 기록**한다(감사 추적).
  - ⑦ 범위 검사는 **가맹점 등록 때만**(범위 1개 이상). CSA 추가·Revision 승인에서는 검사하지 않는다(기존 가맹점 후속 명령 무영향 원칙 유지 — 지금은 서비스 종류가 1개라 결과 차이가 없다).
- 대안: 서비스 종류별로 사업자 계약 여러 개 / 기간 없음(만료 개념 없음, U-4 '만료' 포기) / 정지 해제 2인 / CSA 추가 때 서비스 종류 ∈ 사업자 계약 범위 검사(기존 가맹점 후속 명령에도 영향).
- 영향: ③은 확정 결정 D-FLOW-004 ① 변경이다. ⑦ 대안은 BR-BIZ-279 괄호(D-BIZ-001 원칙)를 바꾼다. 기간 값은 Demo 값이며 운영값이 아니다.
- 막히는 작업: **FLOW-3**, FLOW-2(변경 접수·정지·해지 명령), 사업자 상세 '계약 진행' 섹션.

### Q-ELIG-3 (금융·권리 의미) 사업자 계약 해지·정지·만료 뒤 기존 가맹점

- **권장: (a) 현행 D-FLOW-003 ② 유지·확장** — 해지·정지·만료 모두 **새 가맹점 등록만** 막는다. 기존 가맹점의 신규 승인·취소·매입·정산·지급은 바꾸지 않는다. 화면에 '연결 가맹점 n개 — 개별 중지/철회 필요'를 안내한다(BR-BIZ-312 기준). 신규 승인 중지는 가맹점별 차단 기록·가맹점 계약 철회(MASTER-LIFECYCLE-001)로 한다.
- 대안:
  - (b) 해지·정지 때 연결 가맹점에 **신규 승인 차단 기록을 자동 생성**한다(안전 방향 1인, D-MD-006). 취소·조회·UNKNOWN 복구·미매입 매입·정산은 결제허용 §4.3 표대로 계속한다. 만료는 안내만 한다.
  - (c) 해지 때 가맹점 계약을 자동 철회한다(D-ADMIN-003 '계약 철회' 2인 대상과 충돌 가능).
- 영향: (b)·(c)는 Snapshot 발행·`entitlement_revision` 증가·PAYMENT 판정에 영향을 준다. 차단 기록 명령이 미구현이라(BR-BIZ-061 '생성 명령 미구현') MASTER-LIFECYCLE-001이 먼저 필요하다. 철회 중 진행 승인 사후 처리(PAY.md F-4)도 함께 정해야 한다.
- 막히는 작업: FLOW-2 해지·정지 명령, MASTER-LIFECYCLE-001. **FLOW-3 관문 자체는 막지 않는다**(관문은 새 가맹점만 보므로).
