## 2. 구성

### 2.1 업무 규칙 대장 (정본)

- 위치: `docs/rules/<domain>.md` — 도메인당 파일 하나. `docs/rules/README.md`가 도메인 목록·형식·상태 정의.
- 규칙 1개 = 표 1행. 열: `ID | 규칙 | 상태 | 출처 | 근거 | 적용 명세 | 검증`.
  - **ID**: `BR-<도메인>-<3자리>` (예 `BR-BIZ-014`). 한 번 쓴 ID는 재사용 금지, 대체되면 상태만 바꾼다.
  - **규칙**: 한 문장, 검증 가능한 형태("~이면 ~한다 / 거절한다"). 화면 문구·구현 방식은 규칙이 아니다.
  - **상태**: `확정` / `제안`(사용자 결정 전) / `대체됨→BR-…` / `Demo값`(운영값 아님) / `미결`(질문 ID).
  - **출처**: `사용자`(D-… 답) / `적용`(Coordinator가 어느 답에서 끌어냄 — 다음 보고에서 사용자 확인 전까지 `제안`) / `기준`(baseline 확정 문서) / `관례`(가역 구현 세부 — 원칙적으로 대장에 넣지 않음).
  - **근거**: D-ID, Q-ID, baseline 문서 §.
  - **적용 명세**: 명세 파일 §.
  - **검증**: 시험 파일·시험 이름(없으면 `없음`).
- `DECISIONS.md`는 결정 이력(누가 언제 무엇을 골랐는지)으로 남고, "지금 유효한 규칙"은 대장에서 본다.

### 2.2 착수 전 관문 (Definition of Ready)

기능·배치 시작 전에 규칙 점검표를 채운다. 빈칸 = 질문을 한 번에 묶어 사용자에게.

| 점검 항목 | 확인 |
|---|---|
| 상태·전이 | 상태 목록, 허용 전이 전부, 종결·비가역, 동시 전이 |
| 금액·통화 | 금액 원천, 통화, 반올림, 부분/전액, Snapshot |
| 키·동일성 | 멱등 키, 같은 키 다른 내용, 중복 판정 범위 |
| 권한·승인 | 역할, 1인/2인, 요청자≠승인자 |
| 개인정보·보안 | 등급, 마스킹, 원문 조회, 로그·감사 노출, 보관 |
| 감사·이력 | 무엇을 언제 기록, append-only |
| 실패·복구 | timeout·UNKNOWN, 재전송, 부분 실패 |
| 기존 규칙 충돌 | 대체되는 BR-ID, 정책서 수정 절 |

배치가 참조하는 규칙이 모두 `확정`이어야 구현 시작(`제안`·`미결` 포함 시 WAITING_DECISION).

### 2.3 추적 게이트

하네스 검사 `RULE-TRACE`(후속 구현):
1. 대장 형식(ID 유일·상태 값·근거 존재하는 D-ID/Q-ID).
2. 작업 카드가 참조하는 BR-ID가 `확정`인지.
3. `확정` 규칙의 `검증` 열이 가리키는 시험이 존재하는지(시험 이름/주석에 BR-ID).
4. `대체됨` 규칙 ID를 지키는 시험이 남아 있지 않은지.

### 2.4 변경 통제

- 사용자 피드백·참고 화면 요청은 먼저 **화면 세부 / 업무 규칙**으로 분류해 보고한다.
- 업무 규칙이면: 영향 분석(대체되는 BR-ID, 정책서 절, 영향 시험) → 사용자 결정 → **대장·정책서·DECISIONS를 같은 커밋**에서 수정 → 그 뒤 명세·구현.

## 4. 진행 순서

1. (이 문서) 형식·도메인 확정, 작업 카드 RULE-GOV-001.
2. 도메인별 대장 초안 추출(6개 병렬, 문서만): 결정·기준 문서·명세·코드·시험에서 현재 유효 규칙을 뽑고, 대체 사슬·충돌·정책서 불일치·시험 없는 규칙·미결을 진단 목록으로.
3. 진단 종합 보고 → 충돌·빈칸 사용자 질문(한 번에).
4. 정책서 본문 정합, 대장 확정.
5. 하네스: 착수 전 관문 점검표(작업 카드 필드), RULE-TRACE 검사 구현.
6. 시험에 BR-ID 연결(도메인별 점진).
7. 그 뒤 MERCHANT-FLOW-001 재개(명세의 규칙을 BR-ID로 연결).
